# SMART 종합 개요

AI 채팅으로 송금하고, DART 공시를 검색·분석하는 서비스.

| 글자 | 영역 | 내용 |
|---|---|---|
| **S** | Sending | 송금 |
| **M** | Management | 송금 내역 조회 |
| **A** | AI & Analysis | LangGraph 기반 AI 분석 |
| **R** | RAG & Retrieval | DART 공시 데이터 검색·RAG |
| **T** | Transfer | 공시 데이터 전송·송금 업무 |

---

## 1. 목적 / 개발 관점

- **기능을 늘리기보다, 핵심 기능마다 꼬리 질문 5개에 답할 수 있는 포트폴리오를 만든다.**
  - 예: Redis 캐시를 쓴다면 왜 로컬 캐시가 아닌 Redis인지, TTL은 왜 그 값인지, 응답·부하 속도를 개선하려고 무엇을 했는지
- 포트폴리오이자 개발 기준 문서다.

### 심화 주제

| 주제 | 꼬리 질문 대비 범위 |
|---|---|
| **AI 송금 안전장치** | 금액·수취인 오인식 / 확인 버튼 우회 방지 / 중복 클릭·재시도 / 동시 송금 시 잔액 정합성 |
| **RAG 검색 품질** | 평가셋으로 수치 측정 / 청킹·검색 방식 비교 / 재무 수치 환각 방지 |

### 서버를 둘로 나눈 이유: 장애 격리

- LLM 응답이 느리거나 FastAPI에 장애가 나도 송금·계좌 기능은 정상 동작하도록 AI 기능을 별도 서버로 분리했다.
- 파이썬 AI 생태계를 그대로 쓰고, AI 서버만 따로 확장할 수 있다.

### 원칙

- **기술 도입**: Redis 같은 기술은 필요할 때 도입하고, 도입 이유를 근거로 남긴다.
- **결정 근거 기록**: 개요에는 원칙만 적고, 상세한 근거는 별도 문서에 둔다.
- **성능 측정**: 트래픽을 추정해 목표를 정하고, k6 + Prometheus + Grafana로 성능·부하·정합성을 측정한다(6절).
- **범위**: 핵심 기능 외 디테일은 개발과 문서 모두에서 뺀다.
  - 제외: CSRF 방어, 페이지 보호(비로그인 차단), 입력값 검증·공통 예외 처리, UI 디자인
  - 남김(송금 안전장치와 연결): 계좌 소유자 확인, 비밀번호 해시 저장

## 2. 단계별 로드맵

단계마다 **하나씩만** 바꿔서, 각 변경의 효과를 수치로 따로 설명한다.

| 단계 | 내용 | 근거·측정 |
|---|---|---|
| **1단계 (하루 MVP)** | Spring ↔ FastAPI 내부 REST 연동, Spring은 RestClient | 기준 수치. LLM을 기다리는 동안 Spring 스레드가 묶임 |
| **2단계** | 비동기 전환(WebClient) | Java 17이라 가상 스레드를 쓸 수 없음 → LLM 대기 중 스레드 반납, 동시 처리량 비교 |
| **3단계** | MCP 서버 제작·적용 | 송금·계좌 도구(조회·송금 요청 생성까지, 실행 권한 없음), DART 검색 도구 |

- Spring ↔ FastAPI 구간은 REST(WebClient)까지만 간다. gRPC는 도입하지 않는다.

## 3. 서버 역할 분담

| 서버 | 역할 |
|---|---|
| **Spring Boot** | 금융 트랜잭션·비즈니스 처리. 잔액·충전·송금·내역 합계 등 돈 관련 숫자 계산 |
| **FastAPI** (내부 전용, Spring만 호출) | 채팅·AI 분석 요청을 받아 LangGraph 에이전트 워크플로우 구동. DART 재무 수치는 파이썬 계산 코드로 계산. DART 수집 스케줄러 |

- **LLM은 숫자를 만들지 않는다.** 숫자는 코드가 계산하고, LLM은 받은 숫자를 설명만 한다(재무 수치 환각 방지의 근거).
- **AI 경로에는 송금 실행 권한이 없다.** LangGraph는 조회와 송금 요청 생성까지만 하고, 실제 송금은 사용자가 [보내기]를 누르면 Spring이 실행한다.
- **계좌 비밀번호는 채팅으로 받지 않는다.** 채팅 메시지는 OpenAI와 대화 기록에 남기 때문에, 비밀번호는 확인 카드에서만 받아 Spring이 바로 확인한다.

## 4. 핵심 기능 (1단계 MVP)

- **회원**: 회원가입·로그인(JWT). 여러 사용자가 함께 이용
- **계좌**: 서비스 안에서 가상계좌 개설(계좌 비밀번호 숫자 4자리), 충전 기능
- **송금**: 가상 잔액 송금(실제 돈 아님). 받은 쪽 잔액이 늘어남. 한도 없음
  - 받는 사람 지정: 계좌번호, 자주 쓰는 상대(별칭)
- **AI 채팅 송금**: 확인 카드에 계좌 비밀번호를 넣고 [보내기]를 눌러야 실행. 채팅으로 내역 조회
- **송금 내역(Management)**: 목록 조회. 1단계 안에서 전체 조회 → 오프셋 → 커서 무한 스크롤로 개선하고 단계마다 k6로 측정
- **DART 분석**: 코스피200 기업만. 사업의 내용 요약, 재무 수치 비교(경쟁사 비교 포함). 수주금액·투자금처럼 비교 지표 4개에 없는 숫자는 사업의 내용(RAG)에서 답하고 출처를 표시
- **채팅 기록**: 현재 대화 맥락만 유지(LangGraph 체크포인터 + thread_id). 대화방 목록 화면은 없음
  - MVP는 메모리 체크포인터. 워커 1개에서만 맞게 동작하고, 재시작하면 기록이 사라지며, 대화가 쌓이면 메모리가 늘어난다. 부하·재시작 테스트에서 문제가 확인되면 PostgreSQL 체크포인터로 바꾸고 전후 수치를 남긴다.
  - 기록에는 가린 문장만 남긴다(개인정보는 그래프에 넣기 전에 가림, 인젝션으로 막힌 문장은 기록 제외).

### 채팅 답변

- 스트리밍 없음. 채팅 답변은 요약으로 짧게 준다.
- 긴 보고서는 [상세 보기] → 팝업·새 화면. 내용은 클릭할 때 생성한다.

### DART 경쟁사 비교

| 항목 | 기준 |
|---|---|
| 경쟁사 선정 | 직접 만든 경쟁사 목록 + 사용자 지정 우선. MVP 목록은 주요 업종 일부만(업종 미정), 목록에 없는 기업은 사용자 지정으로만 비교 |
| 개수 | 한 번에 최대 3개 |
| 재무제표 기준 | 연결 우선, 없으면 별도. 비교 대상 모두 같은 기준으로 맞추고 어떤 기준인지 답변에 표시 |
| 기간 | 최근 분기 + 전년 동기 대비 |
| 지표 | 매출액, 영업이익, 당기순이익, 영업이익률(계산 코드가 산출) |
| 표시 | 채팅: 요약 + 표 / 상세 보기: 전체. 차트 없음 |
| 시점 차이 | 같은 분기 공시가 없는 회사는 비교에서 빼고 '미공시'로 표시 |

### DART 데이터 수집

| 데이터 | 출처 | 저장 |
|---|---|---|
| **재무 숫자** | 다중회사 주요계정 API(`fnlttMultiAcnt`, 한 번에 최대 100개 회사 → 코스피200은 2번 호출). 매일 최근 2년(올해·작년) 4개 보고서를 받는다 — 처음 실행이 곧 초기 적재 | 재무 테이블(`financial`, FastAPI 소유). 비교 지표 계정(매출액·영업이익·당기순이익)만, 연결·별도 모두 저장 |
| **사업의 내용** | 정기보고서(사업·반기·분기)의 "II. 사업의 내용"만. 공시검색 API(`list.json`)로 회사별 최신 정기보고서(정정 포함)를 찾고, 공시서류원본파일 API(`document.xml`)로 원문을 받아 해당 부분만 추출 | pgvector(`business_chunk`). 회사별 최신 보고서만 유지: 접수번호가 새로우면 회사 단위로 교체, 같으면 건너뜀 |

- 스케줄러: FastAPI 스케줄러 전용 컨테이너, 하루 1회
- 정정 공시: 수집 때 정정본이 있으면 같은 회사·기간 데이터를 덮어쓴다.
- 초기 적재를 TXT 일괄 다운로드 대신 같은 API로 한다: 8개 기간 × 1~2회 호출이라 일 호출 한도(2만)에 비해 미미하고, 같은 코드 경로라 정정 반영도 매일 자연히 된다.
- 실제 응답으로 확인한 점: 1분기·반기·3분기는 `amount`가 해당 분기 단독이고 `prev_amount`가 전년 동기라 "전년 동기 대비"를 그대로 쓴다. 사업보고서는 연간 값이라 4분기 단독은 연간 − 3분기 누적으로 계산한다. 금융업(은행·보험)은 주요계정에 매출액이 없어 비교에서 '-'로 표시한다.
- 수집 대상 기업은 `ai/app/companies.csv`다(대형주 일부로 시작, 코스피200 전체는 이 파일을 교체). 인증키는 `.env`의 `DART_API_KEY`.
- 사업의 내용 수집 방식(최소 동작): 원문은 well-formed XML이 아니라서 관대한 HTML 파서로 읽고, 표는 행 단위 텍스트로 바꾼다. 같은 소제목 안에서 1,000자까지 묶고(겹침 없음) `text-embedding-3-small`(1536차원)로 임베딩한다. 벡터 인덱스는 두지 않는다(검색이 회사 하나로 좁힌 뒤 수십~수백 행을 훑는다). 청킹·검색 방식 비교는 평가 세트가 생기는 NFR-039에서 한다. `OPENAI_API_KEY`가 없으면 collector는 이 단계만 건너뛴다.
- 실측(대상 30곳, 2026년 반기보고서 기준): 청크 2,528개(회사당 27~279개, 평균 859자), 첫 수집 약 1분, 이후 실행 9초(접수번호가 같아 임베딩 없음). 코스피200으로 넓히면 청크는 대략 1만 7천 개 규모다.

### 사업의 내용 답변(FR-017)

| 항목 | 기준 |
|---|---|
| 의도 | 회사 소개·주요 제품·사업 구조, 수주잔고·투자금처럼 비교 지표 4개에 없는 숫자. 송금·내역·재무 비교가 있으면 그쪽이 먼저 |
| 검색 | 말한 기업을 재무 비교와 같은 방식으로 찾고(정식 이름 일치), 질문을 임베딩해 그 회사 청크만 코사인 거리 상위 5개. 벡터 인덱스 없음. 기업을 못 찾으면 임베딩 호출도 하지 않는다 |
| 답변 | 청크를 `<공시>` 구분자로 감싸 시스템 프롬프트로만 전달하고 대화 기록에는 남기지 않는다. 본문의 `<`는 바꿔서 구분자를 닫거나 흉내 내지 못하게 한다. 본문에 없으면 못 찾았다고 답한다 |
| 출처 | 답변 끝에 기업·보고서·접수번호·소제목을 코드가 붙인다. `reply` 안의 줄이라 API는 그대로다 |
| 안내 | 기업 미지정·수집 대상 아님·미수집·DB 장애는 LLM을 부르지 않고 고정 문장으로 답한다 |

- 실측(로컬 실데이터 30곳·청크 2,528개, 3문항): 검색 SQL 5.5ms(가장 큰 회사 279행), 질문 임베딩 포함 검색 192~1,504ms(중앙값 405ms, 첫 호출은 클라이언트 초기화 포함), 의도 추출부터 답변까지 2.7~9.2초.
- 숫자 환각 가드(NFR-016)와 검색 품질 측정(NFR-039)은 이 위에서 한다. 지금은 "본문 숫자를 그대로 쓰라"는 프롬프트 지시만 있다.

## 5. AI 가드레일

**넓게는 얇게, 하나만 깊게.** 다섯 위치에 최소한으로 깔고, 숫자 환각 가드 하나만 5단계까지 판다.
라이브러리는 쓰지 않고 아이디어만 가져와 파이썬 규칙 + LangGraph 노드로 직접 구현한다.

| 위치 | MVP |
|---|---|
| 입력 | 인젝션 대표 유형 규칙(걸리면 LLM 미호출) + 주민·카드번호 가림 |
| 구조화 | 송금 금액·수취인(계좌번호·별칭)을 스키마로 검증하고 원문과 다시 대조, 빠지거나 애매하면 되묻고 같은 대화에서 이어 받기 |
| 검색 | 공시 본문을 '데이터' 구분자로 감싸서 전달 |
| 출력 | **숫자 환각 가드(깊게)**, 투자 권유 표현, 시스템 프롬프트 유출 감지(카나리 단어) |
| 실행 | 요청ID 1회용·5분 만료·본인 확인·계좌 비밀번호(틀리면 요청ID 폐기 → 새 요청은 채팅 호출 제한을 받아 비밀번호 추측이 느려짐) |

- 걸리면 정상 응답 + 고정 문장 + 판정 코드(`guard`). 가드는 LangGraph 노드이고, 걸리면 조건부 엣지로 바로 종료한다.
- 안전 판정을 LLM에게 맡기지 않는다. 분류 모델(Prompt Guard)은 추후 추가해 규칙만 쓸 때와 전후를 측정한다.

### 숫자 환각 가드 5단계

단계마다 평가 세트로 측정한다. 정답이 재무 테이블에 있어 자동 채점된다. 심화 주제 "재무 수치 환각 방지"의 근거다.
대조 근거는 둘로 나뉜다. 재무 지표 4개는 재무 테이블과 항목·값 쌍으로, 사업의 내용 본문 숫자(수주금액 등)는 검색 조각과 존재 대조하고 출처를 표시한다.

```text
1단계 프롬프트만        → 기준선 환각률                       (MVP)
2단계 숫자 존재 대조    → "다른 항목 숫자" 구멍 재현             (MVP)
3단계 항목·값 쌍 대조   → 구멍 해결                            (MVP)
4단계 표기 정규화       → 조·억·%·반올림 오탐 감소               (추후)
5단계 자리표시자 구조   → 숫자는 코드가 채움, 환각 구조적 0       (추후)
```

### 가져오지 않은 것

| 항목 | 이유 |
|---|---|
| LLM·Llama Guard로 안전 판정 | 판정을 LLM에게 맡기지 않는 원칙. Llama Guard는 t3.small에서 무거움 |
| LangGraph interrupt(사람 승인) | AI 그래프 안에 실행 도구가 남음. SMART는 실행 권한 자체를 뺌 |
| Mem0 장기 기억 | 현재 대화 맥락만 유지 |
| Ragas·TruLens로 가드레일 측정 | 지표가 RAG 답변 품질용이고 LLM 채점이라 결과가 흔들림. 가드레일은 차단율·오탐률, 숫자 가드는 재무 테이블로 자동 채점 |

### 운영·관측

- **호출 횟수 제한**: Spring에서 사용자별 채팅 호출 제한. MVP는 메모리 카운터(사용자당 분당 10회), 서버를 늘리면 Redis로 옮긴다.
- **로그**: 판정 코드와 노드별 소요 시간을 자체 로그 테이블에 기록한다.

### 테스트 구성

**API 단위**(개선 이야기를 수치로)와 **전체 시나리오**(서비스 목표 확인)를 둘 다 한다.
LLM은 "우리 서버의 한계를 재는가, 실제 사용자 경험을 확인하는가"로 나눈다.

| 테스트 | 대상 | LLM | 판정 |
|---|---|---|---|
| 지연 실측 | OpenAI 호출 | 실제 | p50·p95·분포 기록 → 가짜 LLM 입력값 |
| 성능 | 송금 내역 목록(전체 → 오프셋 → 커서) | — | p95 < 500ms |
| 부하 | 전체 시나리오, 목표 93 TPS 유지 | 가짜 | 일반 API p95 < 500ms, 채팅 p95 < 가짜 지연 p95 + 1초, 에러율 < 1% |
| 스트레스 | 약 4,960 VU부터 무너질 때까지 늘림(최소 34,608명까지 확인) | 가짜 | 한계 TPS 기록 → 최대 피크 집중도 역산 |
| 로드맵 비교 | 채팅 메시지: REST(RestClient) → 비동기(WebClient) | 가짜 | 단계별 처리량·스레드 비교 |
| 정합성 | 송금 확정 동시 요청(같은 요청ID 연타, 같은 계좌 동시 출금) | — | SQL 3개: 전체 잔액 합계 불변 / 중복 확정 0 / 음수 잔액 0. 락 없는 버전(기준선)·`FOR UPDATE`·`@Version`과 위반 건수·TPS 비교(측정 브랜치에서만) |
| 실제 검증 | 전체 시나리오, 목표 TPS의 10%로 5분 | 실제 | 판정 없이 기록(체감 시간, OpenAI 에러) |
| 품질 평가 | 아래 평가 세트 | 실제 | 첫 버전이 기준선, 단계마다 같은 세트로 전후 비교 |

품질 평가 세트(단계는 하나씩 추가하며 측정):

| 대상 | 지표 | 단계 |
|---|---|---|
| 숫자 환각 (NFR-016) | 환각률 | 5절 숫자 가드 1~3단계 |
| 송금 발화 (NFR-014) | 금액·수취인 일치율, 되묻기 재현율, 틀린 확인 카드 수(목표 0) | LLM 추출만 → 스키마 검증 → 원문 대조 |
| 인젝션 (NFR-012) | 차단율(공격 세트), 오탐률(정상 세트) | 규칙만 → (추후) Prompt Guard |
| 질문 인식 (NFR-044) | 의도 분류 정확도, 기업명 인식률(구어 표현 포함) | 정식 기업명 일치 → (문제가 확인되면) 별칭 사전 → 오타 허용 |
| 본문 검색 (NFR-039) | Recall@5, MRR | 벡터만 → (문제가 확인되면) BM25(RRF) → 재순위 |

- **기업명 인식 기준선**(`ai/evals/company_names.py`, 20개 발화 × 3회, gpt-5-nano·추론 강도 low, 2026-10-15): 재무 의도 100%(20/20), 기업명 인식(정식 이름 일치) 평균 52%(범위 9~12/20). 실패는 줄임말·구어 표기(삼전·하닉·현대차·네이버·한전 등)와 DART 법인명 차이(`한국전력`→`한국전력공사`)다. 정식명 변환·별칭 사전은 같은 세트·같은 방식으로 전후를 잰다.
- **본문 의도 기준선**(13개 발화 × 3회, gpt-5-nano·추론 강도 low, 2026-10-16): 사업의 내용 21/24(88%), 재무·내역·송금·일반 15/15. 실패는 '투자 계획'(3회 중 2회)·'시장점유율'(3회 중 1회)이 재무로 간 경우다. 같은 프롬프트로 기업명 인식 세트를 다시 돌려 재무 의도 100%(20/20), 기업명 인식 평균 57%(범위 11~12/20)로 기준선과 차이가 없음을 확인했다.

- **가짜 LLM**: 실측 지연 분포를 그대로 재현한다(매번 실측값 중 하나를 뽑음, 시드 고정). 실제 검증으로 "가짜로 잰 결과가 실제와 크게 어긋나지 않음"을 확인한다.
- **OpenAI 429**(실제 구간): 우리 에러와 분리 집계, 재시도 없음. 실행 전 예상 비용(호출 수 × 토큰 단가)을 기록한다.
- **추론 강도**(`OPENAI_REASONING_EFFORT`): gpt-5-nano로 호출당 지연을 실제로 쟀다 — 기본(medium) 4~11초, low 약 2.7초, minimal 약 1.2초. minimal은 의도 추출을 자주 놓쳐(13건 중 3건) low를 기본으로 쓴다. 정식 지연 분포(NFR-029)와 송금 발화 평가 세트는 이후에 같은 방식으로 잰다.
- **측정 환경**: 앱(Spring·FastAPI·PostgreSQL)만 t3.small 사양으로 제한하고, k6·Prometheus·Grafana는 제한 밖에 둔다.
- **LLM이 들어간 측정**: 같은 세트를 3번 돌려 평균·범위를 적는다. "0건"은 "100건 중 0건"처럼 분모와 함께 쓴다.

### 지표 수집

```text
k6 ──remote write──────────────────────────┐
Spring Actuator (HTTP 지연·Tomcat 스레드·DB 커넥션 풀) ─┤
FastAPI (LLM 호출 시간·OpenAI 에러 수·가드 판정 횟수) ──┼──▶ Prometheus ──▶ Grafana (한 화면, 같은 시간축)
postgres_exporter (커넥션·락 대기) ─────────────────────┤
cAdvisor (컨테이너 CPU·메모리) ───────────────────────┘
```

### E2E 테스트(JSP 화면)

- **도구**: Playwright for Java. 서버(Java/Gradle)·AI(Python) 둘뿐인 프로젝트에
  세 번째 언어 툴체인(Cypress 등)을 또 들이지 않는다 — 기존 JUnit 5 테스트와
  같은 언어·같은 명령(`./gradlew test`)으로 돈다. 브라우저 바이너리를 자동
  설치해서 별도 드라이버 관리가 거의 없다(Selenium 대비 장점).
- **실행 방식**: `@SpringBootTest(webEnvironment = RANDOM_PORT)`로 실제
  서버를 띄우고, 기존 `TestcontainersConfiguration`(PostgreSQL)을 그대로
  재사용해 Playwright가 그 포트에 브라우저로 접속한다. 새 인프라를 안 만들고
  이미 있는 테스트 기반 위에 얹는다.
- **범위**: 화면(JSP)이 있는 기능마다 만든다. 지금은 회원가입 → 로그인,
  계좌 개설·충전·대표 변경, 송금 내역(무한 스크롤), 별칭 등록·목록, 채팅 송금
  (메시지 → 확인 카드 → 비밀번호 → [보내기])이다. 채팅의 AI 자리는 가짜
  FastAPI로 대체하고, 확인 카드의 요청ID와 송금·잔액은 실제 Spring·PostgreSQL로
  확인한다. 화면이 없는 기능은 API 통합 테스트로 충분하고, 화면이 생기는
  시점에 그 이슈에서 E2E도 같이 추가한다(AGENTS.md 참고).

## 9. 아키텍처 / 흐름

### 전체 구성

```text
[JSP] ◀──▶ [Spring Boot] ◀──내부 REST──▶ [FastAPI + LangGraph]     [FastAPI 스케줄러]
                 │                               │                        │
                 ▼                               ▼                        ▼
      [PostgreSQL: 회원·계좌·송금 | 재무 테이블 | pgvector(사업의 내용)] ◀──┘
```

### LangGraph 워크플로우 (큰 흐름)

```text
사용자 메시지
   ▼
[의도 분류]
   ├─ 송금   ──▶ Spring 송금 요청 생성 ──▶ 확인 카드 반환
   ├─ 내역   ──▶ Spring 내역 조회 ──▶ 설명
   └─ DART   ──┬─ 재무 테이블 ──▶ 계산 코드(수치·경쟁사 비교) ──▶ 요약 + 표
               └─ pgvector 검색(사업의 내용) ──▶ 요약
```

### 채팅 송금

```text
JSP ─"엄마한테 1만원"─▶ Spring ─▶ FastAPI(LangGraph) ─송금 요청 생성─▶ Spring
                                                      (요청ID 발급, 금액·수취인 고정 저장)
JSP ◀──────────────── 확인 카드(요청ID) ────────────────────────────────┘
JSP [보내기] ─요청ID + 계좌 비밀번호─▶ Spring: 본인 확인 → 비밀번호 확인 → 트랜잭션(잔액 차감·입금·내역 기록)
```

### DART 수집

```text
[매일] FastAPI 스케줄러 전용 컨테이너(collector)
       다중회사 주요계정 API(최근 2년 8개 기간) ─▶ 재무 테이블
       공시서류원본파일 API ─▶ "사업의 내용" 추출 ─▶ 청킹 ─▶ OpenAI 임베딩 ─▶ pgvector
       (정정본은 덮어쓰기, 사업의 내용은 회사별 최신 보고서만)
```
