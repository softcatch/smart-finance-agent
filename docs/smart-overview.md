# SMART 종합 개요

AI 채팅으로 송금하고, DART 공시를 검색·분석하는 서비스.

| 글자 | 영역 | 내용 |
|---|---|---|
| **S** | Sending | 송금 |
| **M** | Management | 송금 내역 조회 |
| **A** | AI & Analysis | LangGraph 기반 AI 분석 |
| **R** | RAG & Retrieval | DART 공시 데이터 검색·RAG |
| **T** | Transfer | 공시 데이터 전송·송금 업무 |

---

## 1. 목적 / 개발 관점

- **기능을 늘리기보다, 핵심 기능마다 꼬리 질문 5개에 답할 수 있는 포트폴리오를 만든다.**
  - 예: Redis 캐시를 쓴다면 왜 로컬 캐시가 아닌 Redis인지, TTL은 왜 그 값인지, 응답·부하 속도를 개선하려고 무엇을 했는지
- 포트폴리오이자 개발 기준 문서다.

### 심화 주제

| 주제 | 꼬리 질문 대비 범위 |
|---|---|
| **AI 송금 안전장치** | 금액·수취인 오인식 / 확인 버튼 우회 방지 / 중복 클릭·재시도 / 동시 송금 시 잔액 정합성 |
| **RAG 검색 품질** | 평가셋으로 수치 측정 / 청킹·검색 방식 비교 / 재무 수치 환각 방지 |

### 서버를 둘로 나눈 이유: 장애 격리

- LLM 응답이 느리거나 FastAPI에 장애가 나도 송금·계좌 기능은 정상 동작하도록 AI 기능을 별도 서버로 분리했다.
- 파이썬 AI 생태계를 그대로 쓰고, AI 서버만 따로 확장할 수 있다.

### 원칙

- **기술 도입**: Redis 같은 기술은 필요할 때 도입하고, 도입 이유를 근거로 남긴다.
- **결정 근거 기록**: 개요에는 원칙만 적고, 상세한 근거는 별도 문서에 둔다.
- **성능 측정**: 트래픽을 추정해 목표를 정하고, k6 + Prometheus + Grafana로 성능·부하·정합성을 측정한다(6절).
- **범위**: 핵심 기능 외 디테일은 개발과 문서 모두에서 뺀다.
  - 제외: CSRF 방어, 페이지 보호(비로그인 차단), 입력값 검증·공통 예외 처리
  - 화면 스타일은 현대닷컴(hyundai.com/kr/ko/e) 톤의 공통 CSS(`static/css/smart.css`) 하나만 둔다. 화면별 디자인·컴포넌트 라이브러리는 만들지 않고, 폰트·로고·이미지는 쓰지 않는다. Vue PWA로 옮길 때 이 CSS의 토큰을 그대로 가져간다.
  - 남김(송금 안전장치와 연결): 계좌 소유자 확인, 비밀번호 해시 저장

## 2. 단계별 로드맵

단계마다 **하나씩만** 바꿔서, 각 변경의 효과를 수치로 따로 설명한다.

| 단계 | 내용 | 근거·측정 |
|---|---|---|
| **1단계 (하루 MVP)** | Spring ↔ FastAPI 내부 REST 연동, Spring은 RestClient | 기준 수치. LLM을 기다리는 동안 Spring 스레드가 묶임 |
| **2단계** | 비동기 전환(WebClient) | Java 17이라 가상 스레드를 쓸 수 없음 → LLM 대기 중 스레드 반납, 동시 처리량 비교 |
| **3단계** | MCP 서버 제작·적용 | 송금·계좌 도구(조회·송금 요청·예약 송금 초안 생성까지, 실행 권한 없음), DART 검색 도구. 에이전트 호출은 입장 제어로 막는다(7절) |
| **4단계** | 캐싱(성능 개선) | 자주 묻는 질문에서 LLM 호출을 건너뛴다 → 히트율·p95·LLM 호출 수·비용을 캐시 없음과 비교 |

- Spring ↔ FastAPI 구간은 REST(WebClient)까지만 간다. gRPC는 도입하지 않는다.

### 4단계 캐싱 설계

**LLM 호출 앞에 둔다.** 지연과 비용의 대부분이 LLM 호출이다(5절 실측: 의도 추출 2.3~2.5초, 사업의 내용 답변 6.9초, 재무 조회 29ms). 캐시 적중은 초 단위를 아끼고 저장소 조회는 ms 단위라, 저장소가 로컬이냐 Redis냐의 속도 차이는 선택 기준이 아니다.

**먼저 재고 정한다.** 정규화한 질문의 해시를 로그에 남겨(본문은 남기지 않는다) 상위 질문이 전체에서 차지하는 비율, 곧 히트율 상한을 잰다. 반복이 없으면 도입하지 않는다.

| 대상 | 종류 | 키 | 무효화·TTL | 건너뛰는 것 |
|---|---|---|---|---|
| ① 의도 추출 결과 | 함수 결과 메모이제이션(정확 일치) | 모델·프롬프트·가드 버전 + 가린 질문(정규화) + 진행 중 송금 값 | 버전이 바뀌면 키가 바뀐다. TTL 24시간 | 의도 추출 LLM 2.3~2.5초. 모든 질문 |
| ② 사업의 내용 답변 | 응답 캐시(사용자 간 공유) | 종목코드 + 회사별 최신 접수번호 + 정규화한 질문(새 대화의 첫 질문만) | 새 보고서가 오면 접수번호가 바뀌어 키가 바뀐다. TTL 24시간 | 임베딩·검색·답변 LLM 약 7초 |
| ③ 상세 보기 보고서 | 응답 캐시(공유) | 분석 조건(기업·기간·기준) + 데이터 버전 | 데이터 버전이 바뀌면 키가 바뀐다 | 보고서 생성 LLM. 상세 보기(FR-016) 구현 뒤 |

- **TTL 24시간**: 수집이 하루 1회라 그 안에서는 원천 데이터가 바뀌지 않는다. 새 보고서는 접수번호로 키가 바뀌므로 TTL은 정확성이 아니라 메모리 상한을 위한 값이다.
- **정확 일치만 쓴다.** 의미 유사도(시맨틱) 캐시는 쓰지 않는다. '삼성전자 영업이익'과 '삼성SDI 영업이익'은 임베딩이 가깝지만 답이 다르고, 틀린 답을 내보내는 비용이 느린 응답보다 크다.
- **가드를 통과한 답변만 저장한다.** 걸린 답변·오류 안내는 저장하지 않는다. 가드 규칙·프롬프트가 바뀌면 버전이 키에 들어 있어 이전 항목은 쓰이지 않는다.
- **돈과 사용자 데이터는 캐시하지 않는다.** 잔액·송금 요청·확정·내역은 사용자별이고 정합성이 돈과 직결된다(NFR-009·010). 재무 비교 표도 하지 않는다. 코드가 29ms에 계산해서 건너뛸 것이 없고 항상 최신 수집분이다. 그 질문에서 느린 부분(의도 추출)은 ①이 건너뛴다.
- **대화 맥락이 답에 영향을 주므로** ②는 이전 대화가 없는 첫 질문에만 쓴다. 개인정보를 지우거나 가명화한 문장이 든 질문은 공유 캐시에 넣지 않는다(5절 AI 게이트웨이).
- **하지 않는 것**: 일반 답변(잡담)은 재사용 가치가 낮다. 질문 임베딩 캐시는 ②가 빗나갔을 때만 이득이라(0.2~1.5초) 하지 않는다. OpenAI 프롬프트 캐시는 앞부분이 같은 긴 프롬프트(1,024토큰 이상)에만 듣는데, 추출 프롬프트는 짧고 사업의 내용 프롬프트는 지시문만 같고 공시 본문이 질문마다 달라 효과가 작다.

**구현은 한 번에 하나씩.**

1. **프로세스 내 캐시**(TTL + LRU, 크기 상한). 인스턴스 1대·FastAPI 워커 1개(메모리 체크포인터)라 공유 효과가 같고 인프라가 없다. 값이 작아(답변 1~2KB, 추출 결과 수백 바이트) 1만 건이 약 20MB 수준이다(추정).
2. **Redis**. 아래 중 하나가 측정이나 구성으로 확인되면 바꾼다. (a) 인스턴스가 2대 이상이라 캐시와 호출 제한 카운터(NFR-025)를 공유해야 한다. (b) 재시작·배포로 캐시를 잃는 비용이 크다. (c) 캐시가 프로세스 메모리를 넘는다.
3. 같은 질문이 TTL 만료 직후나 장 시작 직후(피크 30분)에 몰리면 같은 LLM 호출이 겹친다. 키별 락으로 한 번만 호출하고 나머지는 기다린다(single-flight).

**저장소 선택 — CPU 캐시·프로세스·Redis·DB.** 기준은 속도가 아니라 공유·재시작·메모리다(속도 차이는 LLM 지연에 묻힌다, 위).

| 선택지 | 맞는 경우 | 대가 |
|---|---|---|
| CPU 캐시(L1·L2) | 고르는 대상이 아니다. 자주 쓰는 메모리를 하드웨어가 알아서 올린다. 코어당 수십 KB~수 MB라 답변 캐시(1만 건 약 20MB)는 들어가지도 않는다 | — |
| 프로세스 내 캐시 | 인스턴스 1대. 인프라가 없다 | 여러 대면 대마다 따로 데워져 히트율이 나뉘고, 재시작하면 비워진다 |
| Redis | 인스턴스 2대 이상, 재시작에도 유지(위 (a)·(b)) | 운영할 컨테이너가 하나 늘고, 인기 키 하나에 요청이 몰린다 |
| DB 인덱스·요약 테이블 | 캐시가 아니라 원천 조회를 빠르게 한다. 사용자별이고 최신이어야 하는 데이터(내역 추이, 7절) | 쓰기마다 갱신 비용. LLM 결과에는 해당 없다 |

- **사용자가 100만 명이면** 프로세스 캐시(앞, TTL 짧게) + Redis(뒤, 공유, TTL 24시간) 두 단으로 둔다. ②의 키에는 사용자가 없어서 같은 회사·같은 질문이면 누가 물어도 적중하고, 사용자가 늘수록 히트율이 오른다. 앞단은 인기 키가 Redis 한 곳에 몰리는 것을 막는다.

**측정**: 캐시 없음 → 프로세스 캐시(→ Redis)를 한 번에 하나만 바꿔 비교한다. 지표는 히트율, 질문 유형별 p50·p95, LLM 호출 수, 1천 채팅당 비용이다. 질문 풀의 쏠림을 바꿔 가며 히트율별 p95를 함께 낸다. 기준 부하 테스트(NFR-031)는 캐시를 끈 상태로 둔다. 가짜 LLM은 실측 지연 분포를 그대로 쓰므로 캐시 효과는 "히트율 × LLM 지연"으로 설명된다.

### 비용 — 줄인 곳과 남은 곳

돈은 거의 LLM 호출에서 나간다(실제 OpenAI 검증: 호출당 약 $0.0003, 9.3 TPS 5분에 $0.42 — 6절). 인프라는 홈서버 한 대라 클라우드 요금이 없다.

| 지점 | 한 일 | 효과 |
|---|---|---|
| 모델·추론 강도 | gpt-5-nano, 추론 강도 low | 추론 토큰은 출력 요금이라 강도를 낮추면 비용도 준다. 지연도 4~11초 → 약 2.7초(6절) |
| LLM을 부르지 않는 길 | 인젝션 차단, 기업 미지정·미수집 안내, 재무 숫자 계산, 가드 판정을 코드·규칙으로 | 그 턴은 LLM 0회. 기업을 못 찾으면 임베딩도 부르지 않는다 |
| 임베딩 재사용 | 접수번호가 같으면 수집에서 건너뜀 | 첫 수집 뒤로는 매일 실행 9초, 임베딩 0회 |
| 측정 | 부하·스트레스는 가짜 LLM, 실제 OpenAI는 목표의 10%·5분만, 실행 전에 예상 비용 기록 | 50분 스트레스 계단에도 OpenAI 비용 0 |
| 사용자별 한도 | 하루 토큰 한도(기본 50만 ≈ $0.07)와 관리자 정지(NFR-054, 5절 AI 게이트웨이) | 한 사람이 하루에 쓸 수 있는 비용의 상한. 분당 10회 제한(NFR-024)은 순간 폭주만 막는다 |
| 남은 곳 | 4단계 캐시(히트율만큼 호출 감소) | 히트율을 먼저 잰 뒤 도입 |
| 하지 않은 것 | OpenAI 프롬프트 캐시, 벡터 인덱스, Redis | 효과가 작거나 도입 조건 전이다(위 4단계, 4절 검색 5.5ms, 8절) |

## 3. 서버 역할 분담

| 서버 | 역할 |
|---|---|
| **nginx** | 유일한 입구. 도메인 HTTPS를 끝내고 Spring으로 넘긴다(4절, NFR-053) |
| **Spring Boot** | 금융 트랜잭션·비즈니스 처리. 잔액·충전·송금·내역 합계 등 돈 관련 숫자 계산. 송금 완료 알림(SSE). AI 사용 정지·하루 한도 확인, 관리자 API |
| **FastAPI** (내부 전용, Spring만 호출) | 채팅·AI 분석 요청을 받아 LangGraph 에이전트 워크플로우 구동. DART 재무 수치는 파이썬 계산 코드로 계산. DART 수집 스케줄러. LLM 호출은 AI 게이트웨이 한 곳을 지난다(사용량 기록·개인정보 처리·장애 대체, 5절) |

- **LLM은 숫자를 만들지 않는다.** 숫자는 코드가 계산하고, LLM은 받은 숫자를 설명만 한다(재무 수치 환각 방지의 근거).
- **AI 경로에는 송금 실행 권한이 없다.** LangGraph는 조회와 송금 요청 생성까지만 하고, 실제 송금은 사용자가 [보내기]를 누르면 Spring이 실행한다.
- **계좌 비밀번호는 채팅으로 받지 않는다.** 채팅 메시지는 OpenAI와 대화 기록에 남기 때문에, 비밀번호는 확인 카드에서만 받아 Spring이 바로 확인한다.

## 4. 핵심 기능 (1단계 MVP)

- **회원**: 회원가입·로그인(JWT). 여러 사용자가 함께 이용
  - 로그아웃은 화면이 토큰과 대화 기록을 지우고 로그인으로 보낸다. 서버에서 토큰을 무효화하지 않는다(만료 1시간).
- **계좌**: 서비스 안에서 가상계좌 개설(계좌 비밀번호 숫자 4자리), 충전 기능
- **송금**: 가상 잔액 송금(실제 돈 아님). 받은 쪽 잔액이 늘어남. 한도 없음
  - 받는 사람 지정: 계좌번호, 자주 쓰는 상대(별칭)
- **AI 채팅 송금**: 확인 카드에 계좌 비밀번호를 넣고 [보내기]를 눌러야 실행. 채팅으로 내역 조회
- **송금 내역(Management)**: 목록 조회. 1단계 안에서 전체 조회 → 오프셋 → 커서 무한 스크롤로 개선하고 단계마다 k6로 측정
- **알림**: 송금이 확정되면 보낸 사람·받은 사람에게 알린다. 접속 중이면 바로(SSE), 놓친 것은 목록으로(아래 송금 완료 알림)
- **관리자**: 사용자별 AI 사용량 조회, AI 사용 정지·해제(FR-030·031). 관리자는 운영자가 DB에서 지정하고, 화면은 메뉴 없이 주소(`/admin/ai-usage`)로 들어간다(5절 AI 게이트웨이)
- **DART 분석**: 코스피200 기업만. 사업의 내용 요약, 재무 수치 비교(경쟁사 비교 포함). 수주금액·투자금처럼 비교 지표 4개에 없는 숫자는 사업의 내용(RAG)에서 답하고 출처를 표시
- **채팅 기록**: 현재 대화 맥락만 유지(LangGraph 체크포인터 + thread_id). 대화방 목록 화면은 없음
  - MVP는 메모리 체크포인터. 워커 1개에서만 맞게 동작하고, 재시작하면 기록이 사라지며, 대화가 쌓이면 메모리가 늘어난다. 부하·재시작 테스트에서 문제가 확인되면 PostgreSQL 체크포인터로 바꾸고 전후 수치를 남긴다.
  - 기록에는 가린 문장만 남긴다(주민·카드번호·전화번호·이메일은 그래프에 넣기 전에 지우고, 수취인 계좌번호는 그래프 안에서 `[계좌N]`으로 바꾼다. 코드가 만든 답변의 실명은 `[이름]`으로 남긴다 — 5절 AI 게이트웨이 ②. 인젝션으로 막힌 문장은 기록 제외).
  - 화면은 `thread_id`와 말풍선·확인 카드 결과를 탭의 sessionStorage에 두어 메뉴를 옮겨도 같은 대화를 잇는다. [새 대화]로 새로 시작하고, 탭을 닫거나 로그아웃·로그인하면 비운다. 답을 기다리는 중에 메뉴를 옮기면 그 답은 화면에 남지 않는다. 서버에 저장하는 지난 대화 목록은 추후.
- **공개**: 도메인 + HTTPS. nginx가 유일한 입구다(아래 도메인·HTTPS)

- **재검색(NFR-052, 최소 동작)**: 그래프에서 유일하게 되돌아가는 엣지다(`business` → `rewrite` → `business`, 턴마다 1회). 근거는 검색이 정답 청크를 놓친 사례다 — 삼성바이오로직스 수주 질문은 정답 표가 19위였는데 질문을 '수주총액과 수주잔고'로 바꾸면 1위로 잡힌다(6절 본문 검색 기준선).

- 실측(로컬 실데이터 30곳·청크 2,528개, 3문항): 검색 SQL 5.5ms(가장 큰 회사 279행), 질문 임베딩 포함 검색 192~1,504ms(중앙값 405ms, 첫 호출은 클라이언트 초기화 포함), 의도 추출부터 답변까지 2.7~9.2초.
- 숫자 환각 가드(NFR-016)와 검색 품질 측정(NFR-039)은 이 위에서 한다. 지금은 "본문 숫자를 그대로 쓰라"는 프롬프트 지시만 있다.

### 송금 완료 알림(FR-024)

| 항목 | 기준 |
|---|---|
| 대상 | 보낸 사람(출금 알림)과 받은 사람(입금 알림). 보내는 쪽은 Spring |
| 저장 | 확정 트랜잭션에서 알림 2행을 함께 쓴다(`(송금 ID, 받는 사람)` 유일 키). 확정이 롤백되면 알림도 없고, 커밋되면 반드시 남는다 |
| 전달 | 커밋 뒤 접속 중인 사람에게 SSE로 보낸다(E-15). 확정 응답은 전달을 기다리지 않는다 |
| 놓친 알림 | 연결이 없었거나 보내다 실패한 알림은 목록(E-14)에 남아 있다. 다시 연결하면 화면이 목록으로 빈 곳을 채운다 |
| 화면 | 로그인한 화면의 공통 스크립트가 스트림을 연다. 읽음은 화면이 마지막으로 본 알림 ID로 표시한다(서버에 읽음 상태 없음) |
| 연결 유지 | 서버가 하트비트(`: ping`)를 nginx 읽기 제한보다 짧은 간격으로 보낸다 |

- **`EventSource` 대신 `fetch` 스트림**: 브라우저 `EventSource`는 `Authorization` 헤더를 못 붙인다. 토큰을 URL에 넣으면 nginx 접근 로그에 남아서, `fetch`로 헤더를 붙여 스트림을 읽는다(JWT는 localStorage + Bearer, NFR-007).
- **발송 재시도(outbox 릴레이)를 두지 않는다**: 알림 행이 곧 기록이고 SSE는 "지금 알려 주기"라, 보내다 실패해도 잃는 것이 없다(목록에 있다). 별도 발송 워커는 외부 푸시(FCM)를 붙일 때 필요하다.
- **SSE를 고른 이유**: 서버 → 브라우저 한 방향이라 WebSocket보다 단순하고, 끊기면 다시 붙기 쉽다. 브라우저를 닫아도 받는 웹 푸시는 서비스 워커가 필요해 그다음이다.
- **구현(저장)**: `notification` 테이블(Flyway V12)에 `member_id`·`transfer_id`·`direction`(SENT·RECEIVED)·`counterpart_name`·`amount`·`created_at`을 둔다. `(transfer_id, member_id)`가 유일하고 `(member_id, id DESC)` 인덱스가 목록을 받친다. 상대 이름·금액을 행에 함께 두어 목록과 스트림이 조인 없이 같은 모양이다. `TransferService.confirm`이 송금을 저장한 직후 `NotificationService.recordTransfer`로 보낸 사람(SENT, 상대는 받는 사람 이름)과 받은 사람(RECEIVED, 상대는 보낸 사람 이름) 한 줄씩 쓴다. 이 메서드는 `Propagation.MANDATORY`라 확정 트랜잭션 밖에서는 부를 수 없고, 롤백되면 송금과 함께 사라진다. 내 계좌끼리 보내면 받는 사람이 곧 보낸 사람이라 SENT 한 줄만 남는다. `created_at`은 DB 기본값이라 같은 트랜잭션의 송금과 같은 시각이다.
- **구현(전달)**: 저장하면서 `NotificationsSaved`를 발행하고, `NotificationHub`가 `@TransactionalEventListener`(커밋 뒤)로 받아 작업 스레드(`applicationTaskExecutor`)에서 알림 행을 다시 읽어 접속 중인 본인의 연결에만 `event: notification`으로 보낸다. 확정 응답은 이 전달을 기다리지 않고(느린 연결이 막혀 있어도 확정이 끝나는 것을 테스트로 확인했다), 롤백되면 이벤트가 불리지 않는다. 연결 목록은 `회원 ID → SseEmitter 집합`이고, 연결하면 목록에 넣은 뒤 `: connected`를 바로 보내 응답을 시작한다 — 헤더가 나간 시점엔 이미 등록돼 있어서 화면이 그 뒤에 받는 목록과 빈틈이 없다. 보내다 실패한 연결은 목록에서 뺀다. 하트비트 `: ping`은 15초마다 보낸다(nginx 읽기 제한 기본 60초보다 짧다).
- **구현(화면)**: 공통 스크립트(`nav.jspf`)가 토큰이 있으면 `fetch`로 스트림을 열고, 열린 뒤에 목록(E-14 첫 묶음)으로 빈 곳을 채운다(같은 알림은 ID로 한 번만 센다). 끊기거나 못 열면 3초 뒤 다시 열고 그때마다 목록으로 채운다. 헤더의 [알림] 버튼이 안 읽은 수를 보이고, 열면 최근 알림이 보이며 읽은 것으로 한다. 읽음은 `localStorage`의 회원별 "마지막으로 본 알림 ID"이고 다른 탭도 따라간다. 서버에 읽음 상태는 없다.
- **알고 둔 한계**: 연결 목록이 서버 메모리에 있어 서버 1대에서만 맞다. 여러 대면 다른 서버에 붙은 사람에게 닿게 Redis pub/sub이 필요하고(NFR-049 ②), 100만 명 규모는 7절(NFR-045)이다. JWT는 연결할 때만 확인해서 토큰이 만료돼도 열린 연결은 화면을 닫거나 로그아웃할 때까지 유지된다. 안 읽은 수는 목록 첫 묶음(최근 20건) 안에서 센다. 연결 수 제한은 없다.

### 도메인·HTTPS(nginx, NFR-053)

| 항목 | 기준 |
|---|---|
| 역할 | 유일한 입구. TLS를 끝내고(Let's Encrypt, 자동 갱신) Spring으로 넘긴다. 80은 443으로 넘긴다 |
| 공개 범위 | 공유기는 80·443만 nginx로 넘긴다. Spring 8080은 `127.0.0.1`에만 연다 |
| 타임아웃 | nginx > Spring 읽기 제한(채팅 10초·상세 30초) > LLM. 앞단이 먼저 끊으면 끝난 일이 실패로 보인다. 알림 스트림은 버퍼링을 끄고 하트비트 간격보다 길게 둔다 |
| 전달 헤더 | `X-Forwarded-For`·`X-Forwarded-Proto`로 실제 IP와 https를 Spring에 알린다 |
| 요청 제한 | 로그인·가입은 IP별 `limit_req`(분당 10회, 연속 5회까지). 채팅은 사용자별(NFR-024) |
| 측정 | 부하 측정 환경(`smart-loadtest`)은 지금처럼 Spring을 직접 친다. 기준선을 바꾸지 않으려는 것이다(2절 "하나씩만") |

- **왜 지금**: 도메인을 붙이면 로그인 비밀번호·JWT·계좌 비밀번호가 인터넷을 지난다. HTTP로 두면 그대로 보인다.
- **구현**: `nginx/`(Dockerfile·설정 템플릿·진입 스크립트)가 이미지(`smart-finance-agent-proxy`)로 server·ai와 같은 파이프라인으로 배포된다. 설정은 환경변수(`DOMAIN`, `UPSTREAM`)로 채운다. compose에서는 `nginx`·`certbot`이 프로필 `proxy`에 있어서 로컬 개발과 부하 측정(`smart-loadtest`)에는 뜨지 않고, 서버는 `docker compose --profile proxy up -d`로 올린다. 서버 `.env`에 `DOMAIN`·`LETSENCRYPT_EMAIL`이 없으면 배포가 실행 중인 컨테이너를 건드리기 전에 멈춘다(8080이 닫혀 있어서 입구 없이 올리면 밖에서 닿지 않는다).
  - **인증서**: certbot 컨테이너가 HTTP-01(webroot)로 발급받고, 12시간마다 갱신 여부를 본다(`--keep-until-expiring` — 만료 30일 전부터). 받으면 `/certs`에 키 → 인증서 순으로 복사한다. nginx는 인증서가 없으면 자체 서명 인증서로 켜지고(그래야 80번 포트로 도메인을 확인할 수 있다), 진입 스크립트의 감시가 60초마다 `fullchain.pem`의 체크섬을 보고 바뀌면 `nginx -s reload`한다. 못 받는 동안은 10분 간격으로 다시 시도한다(도메인 확인 실패가 시간당 5회 한도에 걸리지 않게). 시험용(`LETSENCRYPT_STAGING=1`)은 인증서 이름이 달라서 진짜로 바꿀 때 지울 것이 없다.
  - **요청 경로**: 80은 인증서 발급 경로만 열고 443으로 301, 443에서 TLS(HTTP/2)를 끝낸다. `Host`·`X-Forwarded-For`(클라이언트가 보낸 값을 믿지 않고 실제 접속 IP로 덮어쓴다)·`X-Forwarded-Proto`를 넘기고, Spring은 `server.forward-headers-strategy=native`로 알아본다(Tomcat이 내부망의 프록시가 보낸 헤더만 믿는다). upstream 이름은 요청마다 Docker DNS로 다시 풀어서, 배포로 Spring 컨테이너가 다시 만들어져 IP가 바뀌어도 따라간다.
  - **읽기 제한·스트림**: 일반 60초(채팅 10초·상세 30초보다 길다). 알림 스트림(E-15)은 버퍼링을 끄고 120초(하트비트 15초보다 길다).
  - **요청 제한**: 로그인·가입은 IP별 분당 10회에 연속 5회까지 허용하고, 넘으면 앱과 같은 JSON 형식의 429 `RATE_LIMITED`를 준다. 둘이 한도를 나눠 쓴다.
  - **막는 경로**: `/internal/**`(Spring의 FastAPI용 내부 API)와 `/actuator/**`는 입구에서 404다(NFR-005와 같은 경계). 서버 안에서 `curl localhost:8080/actuator/health`로 본다. 경로에 세미콜론(`;x=1`, 인코딩된 `%3B`)이 있으면 400으로 거절한다 — nginx는 경로의 일부로 보지만 Tomcat·Spring은 떼어 내고 매핑해서 위 차단·요청 제한을 건너뛰는 데 쓸 수 있기 때문이다(Spring Security 방화벽도 400으로 거절하지만 입구의 보장이 그 기본값에 기대지 않게 한다). 쿼리 문자열의 세미콜론은 상관없다.
- **검증**:
  ① `nginx/test.sh`(CI 잡 `proxy`) — 자체 서명 인증서와 가짜 upstream으로 리다이렉트·인증서 발급 경로·헤더(스푸핑한 `X-Forwarded-For` 덮어쓰기)·차단 경로(세미콜론 경로 400 포함)·스트림 버퍼링(끈 경로는 첫 글자까지 1초, 대조로 켜진 경로는 5초)·읽기 제한 설정·upstream이 바뀌어도 따라감·인증서 교체 후 재로드·요청 제한(연속 20번 중 6번 통과·14번 429)을 확인한다. 각 항목을 빼거나 바꾸면 실패하는 것도 확인했다.
  ② 실제 이미지 조합(Spring·PostgreSQL·nginx, 자체 서명 인증서): 로그인 화면이 HTTP/2로 200, http는 https로 301, 가입·로그인·계좌·송금 확정, 알림 스트림(연결 즉시 `: connected`, 확정하면 이벤트, 15초 간격 `: ping`), 입구에서 `/actuator`·`/internal`은 404(직접 `127.0.0.1:8080`은 200), 로그인 연속 20번은 6번 통과(401) 뒤 14번 429, Spring 8080은 `127.0.0.1`에만 열림.
  ③ certbot: 컨테이너가 실제로 받는 반복 스크립트를 가짜 certbot으로 돌려 인자(`--cert-name`·`--staging`)와 `/certs` 복사를 확인했고, 진짜 certbot이 Let's Encrypt 스테이징에 계정을 만들고 인증 요청까지 가는 것(존재하지 않는 도메인이라 DNS 확인에서 실패)을 확인했다.
  ④ `server.forward-headers-strategy=native`: 실제 Tomcat으로 `X-Forwarded-For`·`X-Forwarded-Proto`를 알아보는지 테스트한다(설정을 빼면 실패).
  ⑤ 부하 측정 환경: `loadtest/run.sh 5 20s`(Spring을 직접 침, nginx는 안 뜸)를 돌려 k6가 `localhost:8080`으로 시나리오 전체(로그인·채팅·송금·내역·가입·상세 보기)를 보내는 것을 확인했다(요청 171건 도달). 실패 1건은 기존에 알려진 사업의 내용 채팅의 10초 읽기 제한이고(이 시나리오의 p95 기준 12.5초 > 10초, 6절 테스트 구성의 부하 테스트 첫 결과와 같다) 포트 변경과 무관하다.
- **알고 둔 한계**: Let's Encrypt 발급·갱신의 성공 경로는 공인 DNS와 80번 포트가 있어야 해서 로컬에서 확인하지 못했다 — 서버의 첫 배포 때 스테이징으로 먼저 본다(README). 공유기 뒤처럼 한 IP를 여럿이 쓰면 로그인·가입 한도를 나눠 쓴다. HSTS·HTTP/3·WAF는 두지 않았다. 입구가 죽으면 밖에서는 접속할 수 없다(8080이 닫혀 있다).
- **다음 단계**: 포트포워딩 대신 터널로 들어오는 포트를 0개로 줄이는 것은 7절(NFR-050)이다.

## 5. AI 가드레일

**넓게는 얇게, 하나만 깊게.** 다섯 위치에 최소한으로 깔고, 숫자 환각 가드 하나만 5단계까지 판다.
라이브러리는 쓰지 않고 아이디어만 가져와 파이썬 규칙 + LangGraph 노드로 직접 구현한다.

| 위치 | MVP |
|---|---|
| 입력 | 인젝션 대표 유형 규칙(판정 전 NFKC·보이지 않는 서식 문자 제거, 걸리면 LLM 미호출) + 개인정보 제거·가명화(아래 AI 게이트웨이) |
| 구조화 | 송금 금액·수취인(계좌번호·별칭)을 스키마로 검증하고 원문과 다시 대조, 빠지거나 애매하면 되묻고 같은 대화에서 이어 받기 |
| 검색 | 공시 본문을 '데이터' 구분자로 감싸서 전달(본문 속 지시를 따른 흔적은 출력에서 검사) |
| 출력 | **숫자 환각 가드(깊게)**, 투자 권유 표현, 시스템 프롬프트 유출 감지(카나리 단어), 간접 인젝션(사업의 내용 답변의 외부 링크·민감값 요구) |
| 실행 | 요청ID 1회용·5분 만료·본인 확인·계좌 비밀번호(틀리면 요청ID 폐기 → 새 요청은 채팅 호출 제한을 받아 비밀번호 추측이 느려짐) |

- 걸리면 정상 응답 + 고정 문장 + 판정 코드(`guard`). 가드는 LangGraph 노드이고, 걸리면 조건부 엣지로 바로 종료한다.

### 출력 가드(구현 범위)

LLM이 쓴 답변(일반 답변·사업의 내용 답변)은 출력 가드 노드를 거쳐야 나간다. 걸리면 고정 문장으로 바꾸고, 대화 기록에도 바뀐 문장만 남는다(샌 문장·믿을 수 없는 숫자가 다음 턴에 가지 않는다).

| 판정 | 방법 | 나가는 답변 |
|---|---|---|
| `PROMPT_LEAK` | 시스템 프롬프트에 심은 카나리 단어가 답변에 있는지(카나리는 프로세스마다 새로 만든다), 또는 답변이 프롬프트 5개(일반·의도 추출·사업의 내용·재검색·상세 보고서) 중 하나와 공백·기호를 뺀 20자 이상 이어서 겹치는지 | 고정 문장 |
| `ADVICE` | 투자 권유 표현 목록. 공시에 나오는 말('비중 확대'·'자기주식 매수')은 넣지 않는다 | 고정 문장 |
| `INDIRECT_INJECTION` | 사업의 내용 답변에만: 외부 링크(URL·www·도메인 모양, 이메일 도메인 포함)나 비밀번호·OTP·PIN·인증번호·보안카드를 입력·전달하라는 문형(NFR-023). 공시 본문에 심은 지시를 모델이 따른 흔적이다 | 재검색 없이 고정 문장 + 출처 |
| `NUMBER_UNVERIFIED` | 답변의 숫자가 LLM에 준 근거에 있는지(2단계). 사업의 내용 답변은 공시 블록, 상세 보고서는 표다. 질문에 쓴 숫자나 이전 답변은 근거가 아니다 | 사업의 내용은 먼저 한 번 재검색(NFR-052), 그래도 걸리면 고정 문장 + 출처(상세 보고서는 재검색 없이 표) |

- 재무 표·요약 문장·내역·송금 확인 문장은 코드가 만들어서 가드 대상이 아니다(NFR-002). 일반 답변은 근거가 없어 숫자를 대조하지 않는다.
- 겹침 검사는 프롬프트를 정의하는 곳에서 `guarded_prompt()`로 감싸 등록한 원문과 비교한다(카나리가 없는 의도 추출·재검색 프롬프트도 지킨다). 번역·요약·번호를 끼워 쪼갠 유출은 못 잡는다(LLM 판정은 추후).
- 의도 추출이 뽑은 기업 이름은 코드 답변("찾지 못한 기업: …")에 그대로 되풀이되고 출력 가드를 거치지 않는다. 30자를 넘는 이름은 기업 이름으로 쓰지 않는다(상장사 정식명보다 넉넉한 길이, 수집 대상 30곳 중 가장 긴 이름은 9자) — 기업 이름 자리에 넣은 공격 문장이 화면에 나오지 않는다.
- 판정 순서는 `PROMPT_LEAK` → `ADVICE` → `INDIRECT_INJECTION` → `NUMBER_UNVERIFIED`다. 간접 인젝션이 숫자보다 먼저라 걸린 답변은 재검색하지 않는다.
- 간접 인젝션 판정은 일반 답변에 쓰지 않는다 — "송금할 때 계좌 비밀번호를 입력해 주세요" 같은 정상 안내가 있을 수 있다. 상세 보고서는 근거가 재무 표(DB 숫자)라 공시 본문이 들어가지 않아 쓰지 않는다.
- 한계: 규칙이라 다른 낱말·동사('접속 암호를 적어'·'인증 코드를'·'비밀번호를 말씀해')나 풀어 쓴 링크('에스엠에이알티 닷컴'·`hxxps://evil[.]com`)는 놓친다. 공시 본문에 정상으로 실린 주소(정부·DART·회사 사이트)를 답변이 옮기면 막힌다 — 허용 목록은 오탐이 문제로 드러나면 그때 정한다. 수집 때 지시문 탐지·LLM 판정은 추후다.
- 근거 텍스트(공시 블록)는 상태에 두지 않고 노드 안에서 대조한다. 체크포인터에 본문이 쌓이지 않게 하려는 것이다.
- 안전 판정을 LLM에게 맡기지 않는다. 분류 모델(Prompt Guard)은 추후 추가해 규칙만 쓸 때와 전후를 측정한다.

### 숫자 환각 가드 5단계

단계마다 평가 세트로 측정한다. 정답이 재무 테이블에 있어 자동 채점된다. 심화 주제 "재무 수치 환각 방지"의 근거다.
대조 근거는 둘로 나뉜다. 재무 지표 4개는 재무 테이블과 항목·값 쌍으로, 사업의 내용 본문 숫자(수주금액 등)는 검색 조각과 존재 대조하고 출처를 표시한다.

```text
1단계 프롬프트만        → 기준선 환각률                       (MVP)
2단계 숫자 존재 대조    → "다른 항목 숫자" 구멍 재현             (MVP)
3단계 항목·값 쌍 대조   → 구멍 해결                            (MVP)
4단계 표기 정규화       → 조·억·%·반올림 오탐 감소               (추후)
5단계 자리표시자 구조   → 숫자는 코드가 채움, 환각 구조적 0       (추후)
```

- **구현 현황**: 1·2단계는 사업의 내용 답변과 상세 보고서(FR-016)에 적용했다(측정은 6절). 채팅의 재무 표와 요약 문장은 코드가 만들기 때문에 환각이 구조적으로 없다. 3단계(항목·값 쌍 대조)의 대상은 LLM이 재무 숫자를 쓰는 상세 보고서이고, 평가 세트와 함께 따로 한다.
- **2단계의 한계**: 숫자 값이 근거에 있기만 하면 통과한다(다른 항목의 숫자여도). 단위·표기만 다른 같은 값(131조 ↔ 131,895,033백만원)과 LLM이 더한 합산 값은 걸린다. 날짜(`2026.06.30`·`'26.1.1`)는 년·월·일로 쪼개 대조한다.

### 가져오지 않은 것

| 항목 | 이유 |
|---|---|
| LLM·Llama Guard로 안전 판정 | 판정을 LLM에게 맡기지 않는 원칙. Llama Guard는 t3.small에서 무거움 |
| LangGraph interrupt(사람 승인) | AI 그래프 안에 실행 도구가 남음. SMART는 실행 권한 자체를 뺌 |
| Mem0 장기 기억 | 현재 대화 맥락만 유지 |
| Ragas·TruLens로 가드레일 측정 | 지표가 RAG 답변 품질용이고 LLM 채점이라 결과가 흔들림. 가드레일은 차단율·오탐률, 숫자 가드는 재무 테이블로 자동 채점 |

### 운영·관측

- **호출 횟수 제한**: Spring에서 사용자별 채팅 호출 제한. MVP는 메모리 카운터(사용자당 분당 10회), 서버를 늘리면 Redis로 옮긴다.
- **로그**: 판정 코드와 노드별 소요 시간을 자체 로그 테이블(`chat_log`: thread_id, guard, node_ms, created_at)에 기록한다. 메시지 본문은 남기지 않는다. 응답을 보낸 뒤 백그라운드로 쓰고, 쓰기에 실패해도 채팅은 무관하다. 노드 시간은 그래프 스트림 이벤트 사이 간격이다. 같은 노드를 두 번 지나면(재검색, NFR-052) 시간을 더하고, `node_ms`에 `rewrite`가 있으면 재검색한 턴이다.
  - 실측(로컬, 실제 OpenAI): 의도 추출 2.3~2.5초, 사업의 내용 답변 6.9초, 일반 답변 1.6초, 재무 조회 29ms, 가드 노드 1~2ms

### AI 게이트웨이(NFR-054~056)

LLM 호출은 모두 FastAPI의 LLM 객체 하나(`get_llm()`)를 지난다. 프롬프트와 응답 사이인 이 자리에 세 가지를 붙인다.

| 육하원칙 | 내용 |
|---|---|
| 누가 | 모든 LLM 호출(의도 추출·답변·재검색·상세 보고서). 기록·한도는 사용자별, 정지·해제는 관리자(FR-030·031) |
| 언제 | 부르기 전(개인정보 처리), 받은 뒤(사용량 기록), 실패했을 때(대체). 한도 확인은 Spring이 채팅·상세 보기 전에 |
| 어디서 | FastAPI 안의 LLM 객체 하나. 별도 서비스로 빼지 않는다(8절 도입 조건) |
| 무엇을 | ① 사용량 기록·하루 한도 ② 개인정보 제거·가명화 ③ OpenAI 장애 시 Claude 대체 |
| 왜 | 도메인을 붙이면 누구나 가입해 내 OpenAI 키로 채팅한다(비용). 채팅 원문이 외부 회사로 간다(개인정보). OpenAI가 멈추면 채팅 전체가 멈춘다(가용성) |
| 어떻게 | 아래 |

```text
Spring ─정지·하루 한도 확인─▶ FastAPI ─개인정보 제거·가명화─▶ LLM 객체 ──▶ OpenAI
                                                               │    └─오류·타임아웃─▶ Claude(1번 더)
                                                               └─호출마다 사용량 기록─▶ ai_usage(사용자·모델·토큰·대체 여부)
```

**① 사용량 기록·하루 한도(NFR-054)**

- **기록은 FastAPI가 한다**: 호출마다 사용자·모델·입력·출력 토큰·대체 여부를 `ai_usage`에 쓴다(`chat_log`처럼 FastAPI가 만들고, 같은 DB라 Spring이 바로 읽는다). 사용자는 전달받은 JWT의 `sub`다. Spring이 응답을 받아 기록하면 10초에 끊긴 턴(재검색 턴, 4절)의 토큰이 빠져, 긴 질문만 골라 하면 공짜가 된다.
  - **구현(기록)**: `ai_usage`(회원 ID·모델·입력·출력 토큰·대체 여부·시각)는 첫 기록 때 만들어진다. 모델에 붙은 `LlmMetrics` 핸들러가 호출이 끝날 때 한 줄을 쓴다. 회원 ID는 Spring이 넘긴 JWT의 `sub`를 FastAPI가 읽어(서명은 Spring이 이미 확인했다) 호출 설정의 `metadata.user_id`에 싣는다 — 그래프 안의 호출(의도 추출·답변·재작성·재답변)과 상세 보고서 호출까지 같은 값이 따라간다. 회원 ID를 못 읽는 호출(수집기·평가 스크립트·JWT 없음)과 오류로 끝난 호출은 남기지 않는다. 대체 여부 컬럼은 NFR-056이 채운다.
  - **실측**(실제 OpenAI gpt-5-nano·개발 DB, 채팅 6턴 + 상세 보기 1회, 2026-10-22): 턴마다 LLM 호출 수와 `ai_usage` 줄 수가 같았고(회원 A 8번·B 1번), 입력·출력 토큰도 `llm_tokens_total`(모델 라벨)과 턴마다 정확히 일치했다(A 입력 12,771·출력 3,449). JWT 없는 요청은 LLM을 2번 불렀지만 줄은 0이다. 기록 1건(연결 + INSERT)은 p50 7.3ms·p95 10.8ms·최대 13.0ms(100건, 로컬 DB)로, 같은 실행의 LLM 호출 평균 6.1초(11번)의 0.1~0.2%다.
  - **알고 둔 한계**: 호출이 끝날 때 동기로 쓴다. DB가 내려가 연결이 거부되면 0.2ms 만에 포기하지만, 패킷이 사라지는 장애(응답 없는 주소로 재 봤다)면 호출마다 연결 대기 5초(`connect_timeout`)가 걸려서 두 번 부르는 턴은 10초 읽기 제한을 넘는다. 이런 장애는 드물고 재무·사업 조회 같은 다른 DB 접근도 함께 막히므로 처음엔 이대로 두고, 필요가 드러나면 백그라운드로 바꾼다. 인덱스는 읽는 쪽(한도 확인·하루 집계)을 재서 정했다(아래 '확인은 Spring이 한다'). 테이블은 첫 기록 때 만들어지므로 Spring은 테이블이 없으면 사용량 0으로 본다.
- **확인은 Spring이 한다**: 채팅(E-11)·상세 보기(E-13) 전에 정지면 403 `AI_BLOCKED`, 오늘(KST) 합계가 한도 이상이면 429 `AI_QUOTA_EXCEEDED`(자정에 풀림). 분당 10회 제한(NFR-024)은 순간 폭주를, 하루 한도는 누적 비용을 막는다.
  - **구현**: `AiUsageGuard`가 FastAPI를 부르기 전에 확인한다 — 채팅(E-11)은 호출 제한(분당 10회) 다음에, 상세 보기(E-13)는 본인 확인 다음에. 정지(`member.ai_blocked`)가 먼저(`AI_BLOCKED`)이고, 오늘 0시(KST) 이후 입력+출력 토큰 합이 한도(`smart.ai.daily-token-limit`, 기본 50만) 이상이면 `AI_QUOTA_EXCEEDED`다. 걸리면 FastAPI를 부르지 않고, 송금·계좌 API는 이 확인을 거치지 않는다. 사용량은 `ai_usage`를 JDBC로 읽는다 — 엔티티로 두면 첫 기록 전에는 테이블이 없어서 JPA 스키마 검증이 시작할 때 실패한다. 테이블이 없으면 0이다.
  - **실측: 한도 확인 쿼리와 인덱스**(`loadtest/ai_usage.sh`, 측정 환경의 DB(2 vCPU·512MiB), 회원 10,000명·최근 30일에 시간 순으로 쌓은 `ai_usage`, 한도 확인 300회·하루 집계 5회·기록 300회, 2026-10-23). 한도 확인은 채팅·상세 보기마다 도는 "이 회원의 오늘 합계"이고, 하루 집계는 관리자 화면(E-16)의 "그날 회원·모델별 합계"다.

    | 표 크기 | 인덱스 | 한도 확인 p50 / p95 / 최대(ms) | 하루 집계 p50 / 최대(ms) | 기록 p50(ms) | 인덱스 크기 |
    |---|---|---|---|---|---|
    | 100만 행(표 81MB, 오늘 18,420행) | 없음 | 14.2 / 16.8 / 28.5 | 24 / 26 | 0.11 | - |
    | | `(user_id, created_at)` | **0.05 / 0.06 / 0.24** | 17 / 22 | 0.13 | 30MB |
    | | `(created_at)` | 0.83 / 0.91 / 0.96 | 9 / 9 | 0.11 | 21MB |
    | 1,000만 행(표 730MB, 오늘 184,226행) | 없음 | **250.5 / 324.3 / 648.0** | 306 / 343 | 0.11 | - |
    | | `(user_id, created_at)` | **0.37 / 1.17 / 2.42** | 305 / 455 | 0.35 | 301MB |
    | | `(created_at)` | 13.3 / 16.8 / 31.7 | 42 / 45 | 0.10 | 214MB |

    - **인덱스 없이는 행 수에 비례해 느려진다**: 한도 확인이 표를 처음부터 훑어서(Parallel Seq Scan) 100만 행 14ms, 1,000만 행 250ms(p95 324ms, 최대 648ms)다. 채팅 한 턴마다 돌아서, 사용량이 쌓일수록 모든 턴이 그만큼 느려지고 턴마다 표를 훑는다.
    - **`(user_id, created_at)`를 두었다**: 회원 한 명의 오늘 줄만 읽어(Index Scan) 1,000만 행에서 0.37ms(p95 1.17ms)로 약 680배 빨라진다. 기록(INSERT)은 p50 0.11 → 0.13ms(100만 행)·0.35ms(1,000만 행)로 LLM 호출(수 초)에 비해 무시할 수준이고, 크기는 표의 41%(301MB)다. `(created_at)`만으로는 오늘 하루치 18만 줄을 훑고 회원으로 걸러야 해서 13ms에 그쳐 고르지 않았다. 정의는 FastAPI의 `ai_usage` 스키마(`store.py`)에 있다.
    - **하루 집계는 인덱스를 더 두지 않았다**: 채택한 인덱스는 하루 집계에 쓰이지 않아 표를 훑는다. 1,000만 행에서 p50 305ms·최대 455ms(5회)로 일반 API 기준(p95 500ms) 안이지만 여유가 크지 않다. `(created_at)`을 더하면 42ms지만 LLM 호출마다 쓰는 인덱스가 하나 더 늘어서, 관리자 화면 한 곳을 위해 지금은 두지 않는다. 행 수에 비례해 늘어 1,100만 행 안팎에서 500ms를 넘으면 더한다.
  - **알고 둔 한계**: 인덱스는 FastAPI의 `ensure_schema`가 `CREATE INDEX IF NOT EXISTS`로 만든다. 새 환경은 표와 함께, 이미 표가 있는 환경은 collector가 시작할 때(DART 키가 있으면) 만들어진다. 표가 커진 뒤 처음 만들면 만드는 동안 기록이 막힌다(`CONCURRENTLY`가 아님) — 이 기능이 나가는 지금은 표가 작다. 채팅 시나리오 부하 테스트(NFR-031)는 다시 재지 않았다: 가짜 LLM은 토큰을 0으로 돌려줘 한도에 걸리지 않고, 확인 쿼리는 0.05ms다.
- **한도 값**: 기본 50만 토큰/일 ≈ $0.07. 실측 평균(호출당 입력 1,529 + 출력 550토큰, gpt-5-nano)으로 LLM 호출 약 240회다. 확인 → 호출 → 기록 순이라 마지막 한 턴만큼 넘을 수 있다. 미리 예약해 정확히 막으려면 턴마다 쓰기가 늘어 하지 않는다.
  - **동시 요청은 그 수만큼 넘는다**: 한도 바로 아래에서 같은 회원이 동시에 30건을 보내면 모두 같은 합계를 보고 통과한다. 채팅은 분당 10회 제한(NFR-024)이 묶어 10건만 FastAPI에 닿았고(20건 429), 상세 보기는 호출 제한이 없어 30건이 모두 닿았다(서버 테스트로 재 봤다). 다만 넘은 뒤에는 그 호출들의 기록이 쌓여 다음 요청부터 막힌다. 검사부터 기록까지 사용자별로 직렬화하려면 LLM을 기다리는 몇 초 동안 잠금이나 DB 연결을 잡아야 하고(서비스가 트랜잭션을 걸지 않는 이유와 어긋난다), 메모리 잠금은 서버를 늘리면 깨진다. 동시 처리 상한은 7절 NFR-049 ①(입장 제어)에서 다룬다.
- **지표**: Prometheus에는 모델별 합계만 둔다(`llm_tokens_total`에 모델 라벨). 사용자 ID를 라벨로 넣으면 사용자 수만큼 시계열이 생긴다. 사용자별은 DB에서 모아 관리자 화면(E-16)에 보인다.
- **관리자(FR-030·031)**: 회원에 역할(USER·ADMIN)을 두고 운영자가 DB에서 지정한다. 아이디 목록 설정으로 정하면 그 아이디로 먼저 가입한 사람이 관리자가 된다. 관리자 API는 요청마다 DB의 역할을 본다(JWT에 넣지 않아 바꾸면 바로 적용). 정지는 AI만 막고 송금·계좌는 그대로다(1절 장애 격리와 같은 경계).
  - **구현**: `member.role`(`USER`·`ADMIN`, 기본 `USER`)은 가입할 때 `SMART_ADMIN_LOGIN_IDS`(쉼표로 구분)에 든 아이디면 `ADMIN`이다. 아이디가 유일해서 그 아이디로 먼저 가입한 사람이 관리자다. 이미 가입한 회원은 운영자가 `UPDATE member SET role = 'ADMIN' WHERE login_id = '…'`로 지정한다. 관리자 API(E-16·E-17)는 요청마다 `member.role`을 읽어 `ADMIN`이 아니면 403 `ADMIN_ONLY`다.
  - **사용량 조회(E-16)**: 그날(KST) `ai_usage`를 회원·모델별로 묶어 회원별로 합치고 입력+출력 토큰이 많은 순으로 돌려준다. 비용은 모델별 단가(`AdminService`의 `PRICES` — gpt-5-nano 입력 $0.05·출력 $0.40, Claude Haiku 5.5 입력 $0.10·출력 $0.50, 백만 토큰당)로 추정한 값이고 단가가 없는 모델은 0으로 센다. 정지된 회원은 그날 사용이 없어도 0으로 목록에 둔다 — 정지하면 새 사용량이 생기지 않아서, 빼면 다음 날부터 화면에서 해제할 길이 없다.
  - **화면**: `/admin/ai-usage`(`admin-ai-usage.jsp`)는 다른 화면처럼 누구나 열 수 있고 데이터 API가 관리자가 아니면 403으로 막아 "관리자만 사용할 수 있습니다"가 보인다. 날짜(기본 오늘 KST)를 골라 조회하고, 행마다 사유를 적어 [정지]·[해제]한다. E2E는 정지 → 채팅 403 `AI_BLOCKED` → 해제 → 채팅 성공까지 본다.
  - **알고 둔 한계**: 사유는 마지막 변경의 것만 남긴다(이력·처리한 관리자는 기록하지 않는다).

**② 개인정보 제거·가명화(NFR-055)** — 기준은 "LLM이 그 값을 알아야 하는가"다.

| 값 | LLM이 알아야 하나 | 처리 |
|---|---|---|
| 주민·카드번호(지금), 전화번호·이메일(추가) | 아니다 | **제거**: `[전화번호]`처럼 바꾸고 되돌리지 않는다 |
| 수취인 계좌번호 | 값은 몰라도 어느 계좌인지는 가리켜야 한다 | **가명화**: `[계좌1]`로 보내고, 송금 요청 도구(I-03)를 부르기 직전에 코드가 되돌린다. 대응표는 서버의 대화 상태에만 둔다 |
| 실명 | 규칙으로는 못 잡는다(기업명·일반 명사까지 잡는다) | **구조로 피한다**: 송금은 별칭·계좌번호로만 받는다. 코드가 만든 답변(확인 문장·내역)의 실명은 화면에만 보이고 대화 기록에는 자리표시자로 남긴다 |
| 계좌 비밀번호·OTP·인증번호 | 아니다 | 채팅으로 받지 않는다(3절 — 확정 비밀번호는 확인 카드 입력란으로 Spring에 바로 간다). 사용자가 채팅창에 잘못 치면 **제거**: 그 낱말 옆 숫자를 `[비밀번호]`로 |

- **구현 전에 새던 곳**: 사용자 메시지의 전화번호·이메일·계좌번호 원문, 의도 추출 프롬프트에 실리는 진행 중 송금 값(계좌번호), 대화 기록에 그대로 들어가는 확인 문장("김영희님께 …")과 내역 답변("- 10/22 김영희에게 …")의 실명이다.
- **검증**: 개인정보 문장 세트로 LLM에 간 원문 0건과 오탐률(금액·날짜를 잘못 지우는지)을 잰다. 송금 발화 세트(NFR-014)의 금액·수취인 일치율이 가명화 전과 같은지 본다.
  - **구현**: 규칙은 `guard.py`에 있다(라이브러리 없이 정규식).
    - 제거: 주민·카드번호에 더해 전화번호(휴대·지역번호 유선, 국가번호 `+82`가 있으면 앞 0을 생략한 `+82 2-1234-5678`도)와 이메일을 `[전화번호]`·`[이메일]`로 바꾼다(`mask_pii`). 엔드포인트가 그래프에 넣기 전에 하므로 체크포인터에도 남지 않는다. 금액·날짜·접수번호·종목코드는 바뀌지 않는다.
    - 비밀번호(#96): '비밀번호·비번·PIN·OTP·인증번호·보안카드' 낱말 가까이(뒤로는 조사·기호 몇 글자, 앞으로는 6자 안)의 4~8자리 숫자를 `[비밀번호]`로 바꾼다. 낱말은 남긴다. 단위가 붙은 숫자(`5000원`·`2026년`·`4자리`·`3번`), 날짜 조각, 낱말 없는 숫자는 그대로다.
    - 가명화: 이 서비스가 발급하는 12자리 계좌번호를 그래프의 입력 가드가 `[계좌N]`으로 바꾼다(`pseudonymize`). 같은 번호는 같은 표기, 새 번호는 다음 번호이고 대응표는 대화 상태(`pseudonyms`)에만 둔다. 의도 추출 프롬프트에 "`[계좌1]` 같은 표기는 가려 둔 계좌번호"라는 안내를 더했고, 진행 중 송금 값에도 표기만 실린다. `create_request`가 송금 요청(I-03)을 만들기 직전에 원래 번호로 되돌린다(`restore`). LLM이 표기를 꾸며 돌려주면('계좌 [계좌1]'·'계좌1') 하나로 맞추고(`normalize_mark`), 대응표에 없는 표기를 지어내면 계좌번호로 쓰지 않고 수취인을 다시 묻는다.
    - 실명: 확인 문장과 내역 답변은 화면(`reply`)에는 Spring이 준 실명을 쓰고, 대화 기록(`messages`)에는 `[이름]`으로 남긴다. 다음 LLM 호출에 실명이 실리지 않는다.
    - 대체(Claude) 경로는 같은 `messages`를 받으므로 따로 할 일이 없다. 가짜 LLM(부하 측정)은 `[계좌N]` 표기를 알아듣게 고쳤다(안 그러면 송금 시나리오가 확인 카드를 못 만든다).

  - **실측: 송금 발화 세트**(`ai/evals/transfer_utterances.py`, 발화 24개 — 계좌번호 16개·별칭 8개, 단일 턴과 값을 나눠 말하는 2~3턴, 실제 OpenAI gpt-5-nano·추론 강도 low, 금액과 수취인이 모두 맞아야 정답): 같은 세트를 구현 전·후 코드로 번갈아 두 번씩, 매번 3회 반복해 쟀다. 예상 비용은 측정 한 번에 $0.02 안팎(호출 수 × 토큰 단가)이다.

    - 계좌번호 발화의 일치율은 같다. 네 번의 측정 모두 값이 틀린 채로 송금 요청이 만들어진 경우가 없고, 실패는 구현 전·후 똑같이 "요청이 안 만들어진" 경우(예: '송금하고 싶어 / 123456789012 / 8000원'처럼 값을 나눠 말하는 대화를 끝까지 이어 받지 못함)다. 가명화로 생긴 새 실패 유형은 없다.
    - 첫 구현(정규화 전)은 계좌번호 발화가 14.0/16(88%)로 내려갔다. LLM이 표기를 꾸며 돌려줬기 때문이다('계좌 111122223333으로' → `계좌 [계좌1]`, '계좌번호 …, 금액 …' → `계좌1`). 표기를 하나로 맞추는 `normalize_mark`를 넣은 뒤 구현 전과 같아졌다(위 표).
    - 별칭 발화는 구현 전부터 거의 틀린다. LLM이 "엄마한테 3만원 송금해줘"에서 금액만 뽑고 별칭(`alias`)을 비우기 때문이다. 별칭 발화에는 숫자가 없어 가명화가 닿지 않는 기존 문제이고, 두 코드의 차이(2% → 8%)는 한 건 안팎의 흔들림이다. 이 이슈에서 고치지 않았고 NFR-014에서 다룬다.
    - **별칭 추출 수정**(#98, 같은 세트 × 3회, gpt-5-nano·추론 강도 low, 2026-11-01): 평가가 틀린 발화를 의도 추출기가 턴마다 뽑은 값으로 나누게 했더니, 별칭 발화 실패 24건 중 22건이 **별칭을 아예 비운 것**이었다(조사가 붙거나 다른 값을 넣은 경우는 0). 의도 추출 프롬프트와 `alias` 필드 설명에 "받는 사람을 엄마·친구처럼 부르면 그 말이 별칭이고 '한테·에게·께'만 뗀다"는 규칙과 예시를 넣었다.

      |---|---|---|
      | 별칭 8개 | 0.7/8(8%, 범위 0~1) | **8.0/8(100%, 범위 8~8)** |

      - 측정 도구: 답변 모델에도 재시도를 걸었다. OpenAI 응답이 간헐적으로 늘어진 날에는 타임아웃 하나가 측정을 멈췄고, 재시도를 건 기준선 측정도 3시간 50분 걸렸다(같은 세트가 정상일 때는 3분 32초).
      - 개인정보 평가는 LLM이 받은 글(시스템 프롬프트 포함)에 값이 들어 있는지 글자로 보므로, 프롬프트 예시 금액 `30000`에 들어 있는 비밀번호 테스트 값 `0000`을 유출로 셌다. 테스트 값을 `0819`로 바꿨다(실제 유출 아님).
  - **알고 둔 한계**: 계좌번호는 이 서비스가 발급하는 12자리 숫자만 가명화한다(다른 은행 계좌·하이픈 표기는 수취인으로 쓸 수 없어 범위 밖). 12자리 숫자는 금액이어도 가린다(콤마 없는 12자리 금액은 1천억 원 이상이다). 비밀번호는 낱말이 있어야 가린다 — 숫자만 치거나(`1234야`) 하이픈·공백으로 쪼갠 숫자(`12-34`)는 그대로 간다. 단위는 숫자에 붙여 쓴 것만 알아본다 — `5000 원`처럼 띄워 쓴 금액이 비밀번호 낱말 바로 옆에 오면 가려진다(띄어 쓴 '원래'·'번호' 같은 낱말 때문에 비밀번호가 새지 않게 한 선택). 실명·주소는 규칙으로 못 잡아서, 사용자가 메시지에 실명을 쓰면 그대로 간다(이름 탐지는 NFR-057). 대화 기록의 `[이름]`은 코드가 만든 답변(확인 문장·내역)만 대상이다. LLM이 쓴 답변이 `[계좌1]`을 되풀이하면 화면에도 그 표기가 보인다 — 복원하면 대화 기록에 번호가 다시 들어가서 하지 않는다. 체크포인터의 원문(`message`)과 대응표는 서버 메모리에만 있고 외부로 가지 않는다. 송금 발화 세트는 NFR-014 평가 세트의 첫 조각이라 금액·수취인 일치율만 잰다(되묻기 재현율·틀린 확인 카드 수는 그 요구사항에서 넓힌다).
- 이름 탐지(한국어 NER)는 탐지율·오탐률을 잰 뒤 도입한다(NFR-057, 추후).

**③ 장애 대체(NFR-056)**

- **방식**: OpenAI가 오류(5xx·429·연결 실패)나 타임아웃이면 같은 요청을 Claude로 1번 더 보낸다(LangChain `with_fallbacks`). Claude는 `langchain-anthropic`(`ChatAnthropic`)으로 붙인다. Anthropic의 OpenAI 호환 엔드포인트는 Anthropic이 시험·비교용이라고 밝혔고 `response_format`·`strict`를 무시해서 쓰지 않는다. 둘 다 실패하면 지금처럼 채팅만 실패한다(`AI_SERVER_UNAVAILABLE`).
- **모델**: 설정값이고 기본은 Claude Haiku 5.5(`claude-haiku-5-5`)다. Claude 5 중 가장 빠른 급이라 10초 턴에 들어갈 여지가 크고, 강제 도구 호출을 지원한다(Opus·Sonnet 5.5는 지원하지 않는다). 단가는 gpt-5-nano보다 조금 높다(100만 토큰당 입력 $0.10·출력 $0.50부터).
- **타임아웃이 먼저다**: 지금 LLM 호출에는 타임아웃이 없다. OpenAI가 응답 없이 멈추면 Spring은 10초에 끊어도 FastAPI 스레드(동기 스레드풀 40개)는 그 호출이 끝날 때까지 묶인다. 호출 종류별 실측 p95에 여유를 둔 값(의도 추출은 실측 3초 안팎이라 5초 등)을 두고, 대체 호출에도 둔다.
- **대체도 턴 안에 끝나야 의미가 있다**: 사업의 내용 답변은 지금도 턴이 10초 제한에 걸려(6절) 느림 대체의 여지가 없다. 빨리 끝나는 오류만 대체가 된다. 실측은 아래.
- **구조화 출력**: `with_fallbacks`는 `with_structured_output`을 양쪽에 같은 인자로 부르고, 방식은 각 클래스의 기본값을 쓴다 — OpenAI는 `json_schema`, Claude는 강제 도구 호출. 따로 만들 것은 없고, 대체 쪽 추출 결과가 같은 스키마로 나오는지만 테스트로 본다.
- **임베딩은 대체하지 않는다**: Claude(Anthropic)에도 임베딩 모델이 없다(Anthropic은 Voyage AI 같은 다른 회사 모델을 권한다). 게다가 공급자를 바꿔도 다른 모델의 벡터는 기존 색인(`text-embedding-3-small`)과 공간이 달라 섞을 수 없다. 임베딩까지 대체하려면 키워드 검색이나 두 번째 색인이 필요하다(NFR-057, 추후). 그전까지 OpenAI 장애 때 사업의 내용 질문은 "지금 공시 본문을 검색할 수 없다"고 안내한다. 재무 비교·송금·내역은 LLM이 의도 추출뿐이라 대체로 돈다.
- **개인정보**: Anthropic은 OpenAI처럼 미국 회사라 대체해도 국외 이전 조건(미국)이 기본 경로와 같다. 대체 경로에도 ②를 거친 입력만 보내고, 공개 서비스로 운영하면 처리방침에 국외 이전(OpenAI·Anthropic)을 적는다.
- **품질**: 출력 가드(숫자·투자 권유·유출)는 모델과 무관하게 그대로 거친다. 대체 모델의 의도 인식률·숫자 가드 통과율은 같은 평가 세트로 따로 잰다(NFR-057, 추후).
- **측정**: 가짜 LLM(6절)에 오류·지연을 넣고, 대체 쪽은 Anthropic 형식(`/v1/messages`) 가짜 응답으로 받아 대체율·턴 p95·실패율을 잰다.
  - **구현**: `main.make_chain(종류, 스키마)`가 호출 종류별 타임아웃(`TIMEOUTS`: 의도 추출 5초·답변 7초·사업의 내용 10초·상세 보고서 30초 — 실측 p95 4.2·5.0·7.8·22.8초와 Spring 읽기 제한 10·30초 사이)을 둔 OpenAI 모델을 만들고, `ANTHROPIC_API_KEY`가 있으면 Claude(`ANTHROPIC_MODEL`, 기본 `claude-haiku-5-5`)를 `with_fallbacks`로 붙인다. 재검색의 재작성은 답변 값을 쓴다. 대체 대상(`FALLBACK_ON`)은 429·5xx·연결 실패·타임아웃이고 400·401 같은 요청·설정 오류는 대체하지 않는다. 구조화 출력은 양쪽 모델에 같은 스키마를 건 뒤 묶는다(`with_fallbacks` 결과에는 `with_structured_output`이 없다). 대체의 오류는 다시 대체하지 않아서, 둘 다 실패하면 Claude의 오류가 올라와 지금처럼 채팅만 실패한다. Claude 호출은 사용량 핸들러가 `ai_usage.fallback = true`로 남기고(NFR-054), Claude의 오류는 `openai_errors_total`에 섞지 않는다. 키가 없으면 대체 없이 OpenAI만 쓴다(타임아웃은 그대로다). 부하 측정 환경은 `ANTHROPIC_API_KEY`를 비워 대체 없이 잰다(기준선 유지).
  - **임베딩 실패 안내**: 검색 임베딩(OpenAI)이 실패하면 사업의 내용 질문은 "지금 공시 본문을 검색할 수 없습니다"로 답하고 채팅은 이어진다(재검색 중이어도 같다). 임베딩 클라이언트는 SDK 기본 재시도(2회)가 남아 있어서 그 대기만큼 안내가 늦어진다(재 보지는 않았다).
  - **실측**(`ai/evals/fallback.py`, 2026-10-22): 가짜 OpenAI·Anthropic 서버에 오류·멈춤을 넣고 실제 FastAPI 앱에 채팅 60턴을 동시 12개로 걸었다(턴마다 LLM 2번: 의도 추출·일반 답변). 지연은 OpenAI 실측 분포를 두 서버 모두에 썼다(Claude 지연은 실측하지 못했다). 성공은 응답 200이고 10초 안(Spring 읽기 제한)이다. 오류·멈춤 비율은 LLM 호출 하나당이다. 실행은 `ai/`에서 `uv run python -m evals.fallback`이고(OpenAI 키·DB 불필요) 몇 분 걸린다.

    | 시나리오 | 대체 | 성공 | 10초 초과 | 오류 | 턴 p50 | 턴 p95 | 대체 호출 |
    |---|---|---|---|---|---|---|---|
    | 정상 | 없음 | 60 | 0 | 0 | 5.9초 | 7.8초 | 0% |
    | 정상 | 있음 | 60 | 0 | 0 | 5.9초 | 7.8초 | 0% |
    | OpenAI 오류 20%(503) | 없음 | 35 | 0 | 25 | 6.2초 | 7.6초 | 0% |
    | OpenAI 오류 20%(503) | 있음 | 60 | 0 | 0 | 5.9초 | 7.8초 | 22% |
    | OpenAI 전체 장애(503) | 없음 | 0 | 0 | 60 | - | - | - |
    | OpenAI 전체 장애(503) | 있음 | 60 | 0 | 0 | 5.9초 | 7.8초 | 100% |
    | OpenAI 멈춤 20%(30초) | 없음 | 35 | 0 | 25 | 6.1초 | 8.7초 | 0% |
    | OpenAI 멈춤 20%(30초) | 있음 | 37 | 23 | 0 | 7.3초 | 15.5초 | 22% |
    | OpenAI·Claude 전체 장애 | 있음 | 0 | 0 | 60 | - | - | - |

    - 정상이면 대체를 켜도 성공·지연이 같고 대체 호출은 0%다. 새 타임아웃은 가짜 분포(최댓값 4.4·5.4·8.8·23.3초)에서 한 번도 걸리지 않았다.
    - 503처럼 빨리 끝나는 실패는 대체가 막는다. 오류 25턴이 0턴이 되고 지연은 그대로이며(p95 7.8초) 대체 호출은 22%다. 전체 장애여도 60턴 모두 답한다.
    - 멈춤은 타임아웃(5~7초)이 먼저 지나야 대체가 시작돼서 답해도 늦다. 오류 25턴은 0턴이 되지만 23턴이 10초를 넘고(p95 15.5초) 10초 안 성공은 35 → 37턴으로 거의 같다. Spring은 10초에 끊으므로 사용자는 이 늦은 답을 받지 못한다. 앞의 "대체도 턴 안에 끝나야 의미가 있다"를 수치로 확인한 것이다. 타임아웃을 줄이거나 Claude가 빠르면 달라지므로 값 조정은 별도 이슈에서 같은 도구로 잰다.
    - 둘 다 멈추면 지금처럼 채팅만 실패한다(60턴 오류).
  - **알고 둔 한계**: 실제 Anthropic API는 호출해 보지 못했다(키가 없다). `ChatAnthropic`의 요청·응답 형식은 가짜 `/v1/messages`로만 확인했고, Claude 지연은 가정이다. 타임아웃 값은 초안이라, 키가 없는 환경도 OpenAI가 느린 날에는 이 시간에 실패할 수 있다. 임베딩에는 타임아웃을 두지 않았다(수집기가 같은 함수로 100개씩 묶어 보내서 채팅 기준 값을 그대로 쓸 수 없다). 대체 경로의 입력은 지금처럼 주민·카드번호만 가린 메시지다(②는 NFR-055).

### 테스트 구성

**API 단위**(개선 이야기를 수치로)와 **전체 시나리오**(서비스 목표 확인)를 둘 다 한다.
LLM은 "우리 서버의 한계를 재는가, 실제 사용자 경험을 확인하는가"로 나눈다.

| 테스트 | 대상 | LLM | 판정 |
|---|---|---|---|
| 지연 실측 | OpenAI 호출 | 실제 | p50·p95·분포 기록 → 가짜 LLM 입력값 |
| 성능 | 송금 내역 목록(전체 → 오프셋 → 커서) | — | p95 < 500ms |
| 부하 | 전체 시나리오, 목표 93 TPS 유지 | 가짜 | 일반 API p95 < 500ms, 채팅 p95 < 가짜 지연 p95 + 1초, 에러율 < 1% |
| 스트레스 | 약 4,960 VU부터 무너질 때까지 늘림(최소 34,608명까지 확인) | 가짜 | 한계 TPS 기록 → 최대 피크 집중도 역산 |

  | 호출 | 쓰이는 곳 | p50 | p95 | 최대 |
  |---|---|---|---|---|
  | 의도 추출(구조화 출력) | 모든 채팅 턴 | 2,953ms | 4,196ms | 4,426ms |
  | 일반 답변 | 일반 질문 | 2,834ms | 5,023ms | 5,408ms |

- **가짜 LLM**(`ai/loadtest/fake_llm.py`): OpenAI 호환 서버다. 앱 코드는 그대로 두고 환경변수만 바꾼다 — 가짜는 `uvicorn loadtest.fake_llm:app --port 9000`(`ai/`에서), FastAPI는 `OPENAI_BASE_URL=http://<가짜>:9000/v1`·`OPENAI_API_KEY=아무 값`.
  - `/v1/chat/completions`(일반 답변·구조화 출력)와 `/v1/embeddings`만 흉내 낸다. 요청 모양(구조화 출력 여부, 프롬프트의 `<공시>`·`<표>`)으로 호출 종류를 가려 위 분포에서 지연을 뽑는다.
  - 장애 대체(NFR-056)용으로 Anthropic 형식의 `/v1/messages`(일반 답변·강제 도구 호출)도 같은 방식으로 답한다(`ANTHROPIC_API_URL=http://<가짜>:9000`·`ANTHROPIC_API_KEY=아무 값`). `create_app`의 `openai`·`anthropic` 인자(`Faults`)로 경로마다 오류(상태 코드)와 멈춤을 비율로 넣는다(시드 고정). `uvicorn`으로 띄운 표준 `app`에는 장애가 없다.
  - 종류마다 시드 고정 난수열을 따로 쓴다(`FAKE_LLM_SEED`, 기본 1). 호출이 섞여도 종류별 순서는 같다. 지연은 `asyncio.sleep`이라 동시 호출이 많아도 OpenAI처럼 스레드를 잡지 않는다.
  - 의도 추출은 시나리오 문장 꼴(송금·내역·재무·사업)을 알아듣는 규칙 기반이고, 답변은 정해진 글이다(숫자가 없어 숫자 가드를 건드리지 않는다). 의도 인식 품질은 실제 LLM으로 `evals/`가 잰다. 앱 이미지에는 넣지 않는다.

  | 재무 비교 | 2,686 · 3,057ms | 2,917 · 2,936ms | +9% · −4% |
  | 사업의 내용 | 6,951 · 6,655ms | 7,329 · 7,326ms | +5% · +10% |
  | 상세 보고서 | 11,662 · 11,251ms | 12,701 · 12,698ms | +9% · +13% |
  | 일반 답변 | 3,673 · 4,309ms | 5,798 · 5,796ms | +58% · +35% |

  - 부하 시나리오에 나오는 턴은 가짜가 실제와 −4%~+13% 안이다. p95는 사업의 내용·상세 보고서가 ±10% 안이고, 재무 비교는 가짜가 낮았다(4.2초 vs 5.3~7.0초 — 20회라 p95는 꼬리 한두 개에 좌우된다).

- **OpenAI 429**(실제 구간): 우리 에러와 분리 집계, 재시도 없음. 실행 전 예상 비용(호출 수 × 토큰 단가)을 기록한다 — 아래 '성능 측정'의 실제 OpenAI 검증.
- **추론 강도**(`OPENAI_REASONING_EFFORT`): gpt-5-nano로 호출당 지연을 실제로 쟀다 — 기본(medium) 4~11초, low 약 2.7초, minimal 약 1.2초. minimal은 의도 추출을 자주 놓쳐(13건 중 3건) low를 기본으로 쓴다. 송금 발화 평가 세트의 첫 조각(금액·수취인 일치율)은 5절 AI 게이트웨이 ②에서 잰다.
- **측정 환경**(NFR-037, `loadtest/`): 앱(Spring·FastAPI·PostgreSQL)만 t3.small 사양으로 제한하고, k6·Prometheus·Grafana는 제한 밖에 둔다.
  - `loadtest/compose.yaml`이 기본 compose 위에 얹는 오버레이다. 앱 세 개를 같은 코어 2개(`cpuset: "0,1"`)에 묶어 t3.small의 2 vCPU처럼 서로 경쟁시키고, 메모리는 합쳐서 2GiB다(Spring 1GiB·`-Xmx512m`, FastAPI 512MiB, PostgreSQL 512MiB). 가짜 LLM(`ai/loadtest/`)은 다른 코어에, k6는 호스트에서 돈다. 개발 환경과 섞이지 않게 compose 프로젝트·이미지 이름을 따로 쓴다(`smart-loadtest`).
  - `loadtest/run.sh [목표 TPS=93] [유지 시간=3m]`: 환경을 새로 띄우고, 시드(`loadtest/seed.py` — 회원 1만, 인당 송금 내역 60건, DART 30곳의 합성 재무와 청크 2,550개)를 넣고, `docker stats`를 3초마다 남기며 k6를 돌려 `loadtest/results/`에 저장한다. Docker VM은 10 CPU·8GB다.
  - 한계: 개발 머신(Docker Desktop, Apple 코어)이라 t3.small의 CPU 크레딧(버스트)은 재현하지 않고 코어 성능도 같지 않다. 절대값보다 어디서 먼저 걸리는지를 본다.
- **부하 시나리오**(NFR-031, `loadtest/k6/scenario.js`): 행동 유형 4개를 세션 도착률로 건다(열린 모델 — 서버가 느려져도 도착률이 줄지 않는다). 목표 93 TPS는 세션 약 16.5개/초이고 유형별로 8.2·4.9·2.5·0.8개/초다. 올리는 30초는 판정에서 뺀다. 합격 기준: 일반 API p95 < 500ms, 에러율 < 1%, 채팅 p95 < 가짜 지연 p95 + 1초. 마지막 기준은 `latency.json`에서 턴마다 호출 지연의 합을 몬테카를로로 구한 값(재무·송금 5,196ms, 사업의 내용 12,535ms, 상세 보기 23,790ms)이다. 읽기 제한(10초)에 막힌 요청은 지연이 10초에서 멈춰 지연 기준만으로는 합격처럼 보일 수 있다 — 그래서 에러율 기준이 따로 필요하다.
- **부하 테스트 첫 결과**(`loadtest/run.sh`, 2026-10-16, 앱 2 vCPU·2GiB, 가짜 LLM — 채팅 질문이 실패하면 세션을 끝내던 시나리오, 그래서 같은 TPS에서 지금보다 부하가 낮다): 목표 93 TPS는 **합격하지 못했다**. 일반 API는 문제가 없고(p95 91ms, 에러 0), 무너지는 것은 채팅이다.

  | 실행 | 일반 API p95 | 재무·송금 채팅 성공 | 사업의 내용 채팅 성공 | 재무 채팅 p95 |
  |---|---|---|---|---|
  | 10%(9 TPS, 1분) | 143ms | 100% | 82%(49/60) | 4.1초 ✓ |
  | 100%(93 TPS, 3분) | 91ms | 5%(재무 86/1,614, 송금 42/955) | 22%(16/74) | 10.0초 ✗ |

  - **사업의 내용 채팅은 부하와 무관하게 10초 읽기 제한에 걸린다.** 10%에서도 18%가 실패했다. 가짜 분포로 턴의 중앙값이 약 8.1초(의도 추출 2.95 + 임베딩 0.18 + 답변 5.0)이고 p95는 10초를 넘는다. 실제 OpenAI로 잰 턴(위 가짜 vs 실제)도 p50 6.7~7.0초, p95 10.8~12.1초라 10초를 넘는 턴이 있다.
  - **FastAPI의 동기 채팅 엔드포인트가 프로세스당 스레드 40개에 묶여 약 28 TPS에서 막힌다.** 채팅은 LLM을 기다리는 동안 스레드를 쥔다. 세션당 스레드-초가 약 7.95(DART 3.0×2 + 8.1, 송금 3.0)라서 40 ÷ 7.95 × 5.65 ≈ 28 TPS다. 같은 환경에서 TPS를 올려 보면 20에서 시작해 30에서 막힌다. CPU는 남는다(FastAPI 평균 12%, DB 7%, 목표 부하에서도). 목표 부하에서 FastAPI 8000 포트로 열린 연결이 90 → 136 → 202개로 쌓였고(6초 간격), Spring 요청 스레드 200개 중 134개가 그 응답을 기다리고 있었다.

  | 목표 TPS(2분) | 재무 채팅 성공 | 송금 채팅 성공 | 사업의 내용 채팅 성공 | 재무 채팅 p95 | 일반 API p95 |
  |---|---|---|---|---|---|
  | 20 | 100% | 100% | 56% | 6.1초 | 95ms |
  | 30 | 96% | 96% | 21% | 9.6초 | 171ms |
  | 45 | 65% | 63% | 12% | 10.0초 | 182ms |
  | 93(3분) | 5% | 4% | 22% | 10.0초 | 91ms |

  - **프로세스를 늘리면 풀리고 다음 병목이 나온다**(실험, 커밋하지 않은 설정). FastAPI를 2개로(스레드 80개) 하면 45 TPS에서 재무 채팅 성공이 65% → 99.9%(798/799)가 된다. 4개로(160개) 93 TPS를 걸면 재무·송금 채팅은 거의 성공하지만(송금 99%) **일반 API p95가 91ms → 약 3초**로 오른다. Spring의 요청 스레드 200개가 전부 채팅 응답 대기에 묶여(덤프 3번 모두 189~200개, 놀고 있는 스레드 0) 로그인 같은 일반 요청이 스레드를 기다린다. CPU는 아직 여유다(Spring 평균 107%·최대 168% / 200%, FastAPI 평균 28%, DB 14%).
  - **CPU는 그다음이다.** BCrypt 검증 한 번이 57ms(p95 67ms)다. 목표 세션 도착률에서 해시가 초당 약 23회(세션당 평균 1.4회: 로그인·가입·계좌 개설·송금 확정)라 코어 약 1.3개가 해시에 든다. 위 실험에서 해시를 계산 중인 스레드가 2~9개 보였다.
  - 개선 후보(각각 별도 이슈, 전후 수치와 함께): ① 사업의 내용 턴이 읽기 제한 안에 끝나게 하거나 제한·표시를 정한다 ② FastAPI 채팅을 비동기로(스레드 대신 이벤트 루프로 LLM을 기다림) ③ Spring의 채팅 대기를 비동기(WebClient)로 — 로드맵 비교(NFR-033)가 이것이다 ④ BCrypt 비용 ⑤ 대화 상태를 프로세스 메모리 대신 DB·Redis로(스트레스 측정에서 FastAPI 메모리가 계속 오르는 것을 관찰).

    | 〃 | 프로세스(워커) 늘리기 | 실험으로 확인(2개면 45 TPS 재무 채팅 성공 65% → 99.9%) | 대화 상태가 워커마다 따로라 ⑤가 먼저다 |
    | 〃 | 비동기(②) | 스레드 없이 LLM을 기다려 동시 처리가 크게 는다 | LangGraph·DB 드라이버까지 async로 바꾸는 큰 변경 |
    | Spring 요청 스레드 200개(70 TPS) | WebClient(③) | 기다리는 동안 스레드를 반납한다 | 리액티브 코드·디버깅 비용. Java 17이라 가상 스레드는 못 쓴다 |
    | 〃 | 인스턴스 늘리기(7절 수평 확장) | 코드 변경이 없다 | 앞단과 무상태화가 먼저 필요하다 |
    | CPU — BCrypt(186 TPS에서 Spring 1.84코어) | 비용 인자 낮추기(④) | 인자를 1 낮출 때마다 해시 시간이 절반 | 무차별 대입에 버티는 힘도 절반 — 보안과 맞바꾼다 |
    | FastAPI 메모리(대화 상태) | DB·Redis로(⑤) | 재시작·여러 워커에도 대화가 유지된다 | 턴마다 읽기·쓰기 왕복 |

  - **고르는 순서**: 먼저 무너지는 곳부터, 효과가 같으면 변경이 작은 것부터 — 대화 상태 DB(⑤) + 프로세스 늘리기 → 그래도 모자라면 비동기(②·③).
- **LLM이 들어간 측정**: 같은 세트를 3번 돌려 평균·범위를 적는다. "0건"은 "100건 중 0건"처럼 분모와 함께 쓴다.

### 지표 수집

```text
k6 ──remote write──────────────────────────┐
Spring Actuator (HTTP 지연·Tomcat 스레드·DB 커넥션 풀) ─┤
FastAPI (LLM 호출 시간·OpenAI 에러 수·가드 판정 횟수) ──┼──▶ Prometheus ──▶ Grafana (한 화면, 같은 시간축)
postgres_exporter (커넥션·락 대기) ─────────────────────┤
cAdvisor (컨테이너 CPU·메모리) ───────────────────────┘
```

- **구현**(NFR-036): 위 그림 그대로다. Prometheus·Grafana·postgres-exporter·cAdvisor는 `loadtest/compose.yaml`에서 앱 제한(코어 2개) 밖의 코어 6~9에서 돈다. `loadtest/run.sh`가 함께 띄우고 k6 결과를 `experimental-prometheus-rw`로 같은 Prometheus에 밀어 넣는다(끄려면 `MONITOR=0`). k6 지연은 p95 게이지가 아니라 native 히스토그램으로 보낸다 — p95 게이지는 라벨별로 따로 계산돼 합칠 수 없고, 히스토그램이어야 이름별 전체 요청의 p95를 구한다(k6 요약의 p95와 같은 실행에서 일반 API 89.5ms vs 92ms, 재무 채팅 5.50초 vs 5.61초로 맞았다). Grafana는 `http://localhost:3000`(로그인 없음, 로컬 전용 포트)이고, 환경을 띄우면 대시보드 "부하 테스트"(패널 16개)가 provisioning으로 홈 화면에 올라온다. 위에서부터 k6 → Spring → FastAPI → PostgreSQL → 컨테이너이고 시간축이 모두 같다.
  - Spring: `micrometer-registry-prometheus` 의존성 하나만 앱에 들어간다. 지표는 측정 환경에서만 `loadtest` 프로파일(`application-loadtest.properties`)로 연다 — `/actuator/prometheus`, 요청 지연 히스토그램, Tomcat 스레드 지표. 기본 설정에서는 열리지 않는다(테스트가 확인한다).
  - FastAPI: `/metrics`(내부망 전용). async라서 동기 스레드풀이 가득 차도 읽힌다. `http_request_seconds`(경로·상태별 지연), `http_requests_in_flight`(처리 중, 스레드를 기다리는 요청 포함), `threadpool_borrowed`·`threadpool_limit`(동기 엔드포인트 스레드풀), `chat_node_seconds`(노드별), `llm_call_seconds`(ok·error), `llm_tokens_total`(입력·출력·모델별, 실제 OpenAI의 비용 계산용 — 사용자별은 DB의 `ai_usage`), `embedding_call_seconds`, `openai_errors_total`(종류별), `guard_decisions_total`(채팅·상세, 코드별).
  - PostgreSQL: postgres-exporter의 커넥션(상태별)과 락, 그리고 추가 질의로 락 대기 수(`pg_lock_waiting_waiting`).
  - 컨테이너: cAdvisor. Docker Desktop(containerd 스토리지)에서는 cAdvisor가 컨테이너 이름을 읽지 못해(`failed to identify the read-write layer ID`) 서비스마다 `cgroup_parent: /lt-<서비스>`를 주고 그 이름으로 CPU·메모리를 본다.
- **병목이 화면에서 보이는지**(2026-10-16, `run.sh` 93 TPS 2분, 앱 2 vCPU·2GiB, 가짜 LLM): 부하 테스트 첫 결과의 병목이 대시보드에 그대로 나왔다. 요청 실패율 22.7%, 채팅 성공은 재무 84/1,123·송금 40/661·사업의 내용 17/70, 일반 API p95 99ms로 첫 결과와 같다.
  - FastAPI: 처리 중 요청이 최대 389개인데 스레드풀은 40/40에 붙어 있다 — 약 350개가 스레드를 기다린다.
  - Spring: Tomcat 일하는 스레드 최대 157/200, Hikari 사용 중 최대 1/10, PostgreSQL 락 대기 0. DB와 커넥션 풀은 병목이 아니다.
  - CPU(코어 수, 앱 한도 2): Spring 최대 1.21, FastAPI 0.20, PostgreSQL 0.19. 노드별 p95는 사업의 내용 약 9초, 의도 추출 약 4.8초다.
- **모니터링 오버헤드**(30 TPS, 90초 유지, 켬·끔 각 1회): 처리량은 같고(요청 2,734 vs 2,749) 일반 API p95는 171ms vs 161ms(+6%), 평균 CPU는 Spring 56% vs 47%(코어 +0.09개), FastAPI 11% vs 10%, PostgreSQL 7% vs 7%였다. 한 번씩 잰 값이라 잡음 안이다.

**송금 내역 목록 — 전체 조회 → 오프셋 → 커서**(NFR-030, 2026-10-20)

- **방법**: 시드(`SEED_HEAVY`)로 내역이 1천·1만·10만·100만 건인 계정을 만들고, 계정마다 `GET /api/v1/transfers?size=20`을 첫 페이지와 전체의 10·50·90·99% 깊이에서 부른다(k6, 건수마다 30초). 깊이별 커서 ID는 DB에서 뽑는다. 판정은 건수·깊이마다 p95 < 500ms다.
  - 계정의 내역은 다른 송금 100만 건 사이에 흩어 넣었다. ID를 연속으로 넣으면 인덱스를 거꾸로 훑기만 해도 끝나서 10ms대로 실제보다 훨씬 빠르게 나온다.
  - 커서는 지금 구현(main 그대로)이다. 전체 조회와 오프셋은 `loadtest/variants/transfer-history.patch`(서비스·컨트롤러에 메서드 2개)를 측정 브랜치에 적용해 같은 방식으로 쟀다. main에는 넣지 않는다: `git apply loadtest/variants/transfer-history.patch` 후 `history.sh offset`·`all`.
- **결과**(깊이별 p95 중 가장 느린 값):

  | 건수 | 커서(현재) | 오프셋 | 전체 조회 |
  |---|---|---|---|
  | 1,000 | 19ms | 19ms | 42ms |
  | 10,000 | 24ms | 25ms | 94ms |
  | 100,000 | 88ms | 165ms | 324ms |
  | 1,000,000 | 17ms | **1,416ms ✗** | **서버 메모리 부족 ✗** |

  오프셋은 100만 건에서 깊이에 따라 달라진다(초당 1건): 첫 페이지 27ms, 10% 지점 943ms, 50% 889ms, 90% 1,416ms, 99% 1,294ms. 커서는 100만 건에서 모든 깊이가 15~17ms다. 요청률은 커서 전체와 오프셋 10만 건까지가 초당 20건, 전체 조회 10만 건까지가 초당 2건, 오프셋·전체 조회의 100만 건이 초당 1건이다.
- **커서**는 1천~100만 건, 모든 깊이에서 p95 88ms 이하로 기준(500ms)의 18% 안이다. 10만 건 계정의 첫 페이지가 가장 느린 것(88ms)은 계정의 내역이 전체 송금에서 차지하는 비중에 따라 PostgreSQL이 다른 실행 계획을 고르기 때문이다(100만 건 계정은 15ms대).
- **오프셋**은 깊이에 비례해 느려진다. 10만 건까지는 통과하지만 100만 건에서는 10% 지점(10만 행 건너뜀)부터 기준을 넘는다. 99만 행을 건너뛰는 질의는 DB 안에서만 826ms(`EXPLAIN ANALYZE`)다. 같은 100만 건에 초당 20건을 걸면 DB가 포화해 p95가 40~48초까지 올랐고 요청의 44%가 실패했다.
- **전체 조회**는 건수에 비례해 느려지고(42 → 94 → 324ms) 100만 건에서는 한 번에 100만 행을 객체로 만들다 서버 힙(512MiB)을 넘겼다. 서버 로그에 `OutOfMemoryError`가 쌓이고 요청 10건 중 9건이 실패했으며, 그 서버는 이어진 요청에도 응답하지 못했다.
- **한계**: 건수마다 30초 한 번씩 잰 값이다. 개발 머신(Docker Desktop)이라 절대값보다 방식 간 차이를 본다. 100만 건 계정은 극단 사례지만, 오프셋·전체 조회가 그 규모에서 깨지고 커서만 남는다는 것이 커서를 고른 이유의 수치다.

**스트레스**(NFR-032, `loadtest/stress.sh`, 2026-10-20, 가짜 LLM)

- **방법**: 같은 환경에서 목표 TPS를 5에서 652까지 단계마다 올린다(올리기 15초 + 유지 120초, 극단 단계인 186 이상은 유지 60초, 단계마다 k6를 따로 돌린다). 판정 없이 요청 이름별 지표를 남기고, 부하 테스트(NFR-031)와 같은 기준으로 단계를 가른다: 일반 API p95 < 500ms, 재무·송금 채팅 p95 < 5,196ms(가짜 지연 p95 + 1초), 실패율 < 1%, 목표 도착률을 채움. 사업의 내용 채팅은 읽기 제한(10초) 때문에 부하와 무관하게 실패해서(위 부하 테스트 첫 결과) 실패율에서 뺐다. **한계 TPS는 기준을 지킨 마지막 단계**다. 단계 사이에는 FastAPI·Spring이 한가해질 때까지 기다려 앞 단계에 밀린 요청이 다음 단계를 흐리지 않게 했다.
  - **세션은 채팅이 실패해도 이어간다.** DART 흐름은 사업의 내용 질문이 읽기 제한에 걸려도 다음 질문과 상세 보기까지 보낸다. 거기서 세션을 끝내면 느려질수록 세션당 요청이 줄어 목표 TPS보다 낮은 부하로 한계를 재게 된다 — 그렇게 쟀을 때 한계는 19 TPS였고, 이어가게 바꾸자 15 TPS로 내려갔다(상세 보고서는 호출당 스레드를 가장 오래 쥔다).

  | 5 | 14 | 14 | 15 | 0.20 |
  | 10 | 31 | 31 | 32 | 0.27 |
  | 14 | 39 | 39 | 43 | 0.29 |
  | 16 | 40 | 51 | 50 | 0.30 |
  | 20 | 40 | 103 | 82 | 0.36 |
  | 30 | 40 | 281 | 100 | 0.46 |
  | 50 | 40 | 983 | 162 | 0.65 |
  | 70 | 40 | 1,609 | 200 | 0.89 |
  | 93 | 40 | 1,685 | 200 | 1.03 |
  | 186 | 40 | 770 | 200 | 1.84 |

  - **FastAPI의 동기 채팅 스레드풀(40개)이 먼저 찬다.** 10 TPS에서 31/40, 14 TPS에서 39/40이고 15 TPS부터 40/40에 붙어 스레드를 기다리는 요청이 줄을 선다(180초로 잰 값: 15 TPS 44개, 16 TPS 57개; 120초 구간 20 TPS 103개 → 50 TPS 983개). 줄 서는 시간이 채팅 p95에 1초 이상 더해지는 지점이 15~16 TPS다. 이론 처리 한계(약 28 TPS, 위 부하 테스트 첫 결과)보다 낮은 이유다. 이때 CPU는 한가하다(Spring 0.3코어, FastAPI 0.1, DB 0.05).
  - 18 TPS부터 채팅 p95가 10초 읽기 제한에 붙어 실패가 생기고 30 TPS에서 26%다. 이 구간까지 일반 API는 문제가 없다(p95 76~121ms).
  - **70 TPS부터 Spring이 막히기 시작한다.** Tomcat 일하는 스레드가 200/200에 차서 일반 API p95가 2.9초로 오르고, 186 TPS에서는 Spring CPU가 한도(2코어)의 92%인 1.84코어에 닿는다(BCrypt 로그인 포함).
- **극단 652 TPS(DAU 전원 동시)**: k6가 도착률의 87%를 걸었다(VU 준비가 도착을 못 따라가 일부를 건너뜀). 서버는 죽지 않았다 — 컨테이너 재시작 0회, 메모리 부족 종료 없음. 요청은 k6 제한시간(60초)까지 밀려 일반 API p95가 60초, 실패율 36%였고 성공 요청은 초당 48개였다. 부하를 끊고 5 TPS를 다시 걸면 기준을 다시 통과했다(일반 API p95 142ms, 실패 0). 한 단계가 끝난 뒤 밀린 요청이 모두 끝나 서버가 한가해지는 데 걸린 시간은 30 TPS까지 5~21초, 40 TPS 이상에서는 46~258초였다.
- **관찰: FastAPI 메모리가 시간에 따라 계속 오른다.** 대화 상태를 프로세스 메모리(`InMemorySaver`)에 둬서, 165MiB로 시작해 50분 계단 실행의 50 TPS 단계에서 한도 512MiB에 닿았다(그 뒤 522MiB에서 평평했고 죽지는 않았다). 14~16 TPS 12분 동안 217 → 290MiB로 올랐다(분당 약 6MiB, 대화 하나에 약 50KB로 추정). 하루 단위의 지속 부하에서는 이 한도가 먼저 문제될 수 있어 개선 후보에 추가한다(대화 상태를 DB나 Redis로).
- **한계**: 단계마다 한 번씩 잰 값이다(한계 근처만 180초 확인). 사업의 내용 채팅의 실패는 부하와 무관한 읽기 제한 때문이라 한계 판정에서 뺐다. 개발 머신(Docker Desktop)이라 t3.small의 CPU 크레딧은 재현하지 않는다. 위 부하 테스트 첫 결과(2026-10-16)는 채팅이 실패하면 세션을 끝내던 시나리오로 쟀기 때문에 같은 TPS에서 부하가 이 절보다 낮다.

**실제 OpenAI 검증**(NFR-035, 2026-10-20)

- **조건**: 전체 시나리오를 목표 TPS의 10%(9.3 TPS)로 5분(올리기 30초는 따로) 걸고, 실제 OpenAI(gpt-5-nano·추론 강도 low)와 가짜 LLM에서 각각 돌려 판정 없이 기록한다(`JUDGE=0`). 두 실행 모두 같은 시드이고, DART 데이터는 합성이 아니라 개발 DB의 실데이터(30곳, 사업의 내용 청크 2,528개)를 복사해 썼다(`DART_FROM_DEV=1`) — 합성 청크로는 실제 모델이 근거 없음으로 짧게 답해 지연이 달라질 수 있다. LLM 호출은 재시도하지 않고(`max_retries=0`) 429는 FastAPI의 `openai_errors_total{type="RateLimitError"}`로 우리 에러(k6의 요청 실패)와 따로 센다.
- **실행 전 예상 비용.** 작은 파일럿(`REAL_LLM=1`, 3 TPS, 2분)을 먼저 실제 OpenAI로 돌려 토큰을 쟀다 — LLM 호출 197회, 입력 301,175·출력 108,290 토큰(호출당 평균 1,529·550), 비용 $0.058, OpenAI 오류 없음. 첫 본 실행은 LLM이 들어가는 세션(DART 분석형·송금형)이 파일럿의 6.55배(파일럿 약 63개 → 본 실행 약 410개)라서 $0.058 × 6.55 ≈ $0.38으로 예상했고 실제는 $0.374였다. 단가는 OpenAI 모델 페이지(2026-10-20 확인)의 gpt-5-nano 입력 $0.05·출력 $0.40/백만 토큰이다. 추론 토큰은 출력에 들어 있고, 캐시된 입력 할인과 임베딩 비용($0.02/백만 토큰, 질문 한 줄)은 반영하지 않았다(상한 쪽).
- **시나리오를 고쳐 다시 돌린다.** 첫 실행의 시나리오는 사업의 내용 채팅이 실패하면(24%) DART 세션이 거기서 끝나 재무 질문과 상세 보고서가 빠졌다. 지금 시나리오는 이어가므로 LLM 호출이 늘어난다 — 세션 약 60개 × (재무 질문 1회 + 상세 보고서 1회) ≈ 120회. 평균 호출 비용($0.374 ÷ 1,288회 ≈ $0.00029)으로 치면 +$0.035, 보고서가 평균의 5배 비싸다고 치면 +$0.11이다. **다시 돌리기 전 예상 비용은 약 $0.45(상한 $0.7)**였고 실제는 $0.420이었다. 가짜 LLM 실행은 비용이 없다.
- **결과**(9.3 TPS, 유지 5분, 유지 구간의 요청 이름별 값):

  | 요청 | 가짜 p50 | 가짜 p95 | 실제 p50 | 실제 p95 | p50 차이(실제 − 가짜) |
  |---|---|---|---|---|---|
  | 재무 채팅 | 2,975ms | 4,236ms | 2,224ms | 3,584ms | −25% |
  | 송금 채팅 | 2,985ms | 4,236ms | 2,324ms | 3,744ms | −22% |
  | 사업의 내용 채팅 | 8,408ms | 10,012ms | 7,543ms | 10,012ms | −10% |
  | 상세 보기 | 13,007ms | 22,814ms | 9,980ms | 18,401ms | −23% |
  | 로그인(BCrypt) | 76ms | 145ms | 80ms | 153ms | +5% |

  - **OpenAI 429는 0건이다**(오류 종류별 합계도 0). 호출 1,411회(가짜 실행 1,417회), 입력 2,121,733·출력 784,466 토큰(분당 약 53만 토큰·257회)이 한도 안이었다. 목표 TPS 전체(93 TPS)는 이 10배라서 계정 한도에 걸릴 수 있다.
  - 재시도는 채팅 LLM만 끈 상태다. 임베딩 클라이언트는 SDK 기본 재시도(2회)가 남아 있어 429가 나도 앱에 오류로 보이지 않을 수 있다. 이번에는 임베딩 248회의 p95가 0.25초라 재시도 대기(0.5초 이상)가 끼지 않았음을 확인했다.
  - **우리 에러는 요청 실패로 센다.** 실제 47건, 가짜 60건이고 모두 사업의 내용 채팅이 Spring → FastAPI 읽기 제한(10초)을 넘긴 것이다(Spring 로그의 AI 호출 실패 49건과 같다). 실제에서 20%, 가짜에서 25%가 실패한다 — 부하와 무관한 기존 문제(위 부하 테스트 첫 결과)가 실제 OpenAI에서도 그대로 나온다. 다른 요청의 실패는 없다.
  - **실제가 가짜보다 22~25% 빨랐다**(재무·송금 채팅, 상세 보기. 사업의 내용은 10%). 가짜의 분포는 4일 전(2026-10-16)에 잰 것이고 OpenAI 지연이 날마다 흔들려서(위 지연 실측) 이 차이는 같은 수준의 편차다. 가짜 LLM은 이 시점의 실제보다 보수적(느린) 쪽이다. 일반 API(로그인 등)는 두 실행이 같다(p95 145 vs 153ms) — 앱 쪽 부하는 LLM이 가짜여도 같다는 뜻이다.
  - **한계**: 목표의 10%, 5분 한 번씩이다. 실제 OpenAI는 날마다 지연이 달라서 이 값은 오늘의 스냅샷이다. 시나리오를 고치기 전 첫 실행(사업의 내용 채팅이 실패하면 세션을 끝내던 시나리오)도 같은 방향이었다(실제가 가짜보다 15~21% 빠름, 429 0건, 비용 $0.374).

### 정합성 측정(NFR-034)

시스템은 바꾸지 않고 `main`의 송금 확정이 동시 요청에서 돈을 지키는지 잰 **기준선**이다. 비교용 변형은 패치 파일로만 두고 `main`에는 넣지 않는다. 측정 환경은 위와 같다(앱 2 vCPU·2GiB).

| 측정 | 실행 | 결과 표 |
|---|---|---|
| 정합성(NFR-034) | `[ROUNDS=100 PARALLEL=10] loadtest/integrity.sh [main\|none\|lock\|version]` | 끝에 자동으로 출력, `<결과 폴더>/report.md`(결과 폴더 `loadtest/results/integrity-<방식>-<시각>/`) |

`none`·`lock`은 `git apply loadtest/variants/transfer-confirm.patch` 뒤에, `version`은 거기에 `transfer-confirm-version.patch`를 더 적용한 뒤에 돌리고, 끝나면 `git apply -R`로 되돌린다.

**송금 확정 동시성 — 현재 구현 → 잠금 없음 → FOR UPDATE → @Version**(NFR-034, 2026-10-20)

- **방법**: 보내는 회원 100명이 시나리오마다 한 번씩 확정을 건다. 확정은 회원당 10개를 한꺼번에 보낸다(k6 `http.batch`, 동시 200건). 회원 1,300명을 시드하고 판정은 끝난 뒤 SQL 3개다: 전체 잔액 합계 불변 / 중복 확정 0(송금 건수 − 사용 처리된 요청 수) / 음수 잔액 0.
  - **같은 요청ID 연타**: 요청 1건(1,000원)을 같은 요청ID로 10개 동시 확정한다. 성공은 1건이어야 한다.
  - **같은 계좌 동시 출금**: 잔액 100,000원 계좌에서 서로 다른 10명에게 30,000원씩 10건을 동시 확정한다. 성공은 3건이어야 한다. 받는 쪽을 달리한 것은 잔액이 틀어졌을 때 전체 합계에서 드러나게 하려는 것이다.
  - **main**은 지금 구현이다: 요청ID는 `UPDATE … WHERE used = false`의 영향 행 수로 선점하고, 출금은 `UPDATE … WHERE balance >= :amount`로 확인과 차감을 한 문장에서 한다. **잠금 없음**은 요청과 계좌를 읽고 계산해서 쓰는 코드, **FOR UPDATE**는 그 코드에 요청·계좌 행 잠금(`PESSIMISTIC_WRITE`), **@Version**은 그 코드에 낙관적 락이다(재시도 없이 충돌은 거절).
  - 방식마다 3회 쟀다. 아래는 최소~최대다.
- **결과**:

  | 방식 | 전체 잔액 합계 차이 | 중복 확정 | 음수 잔액 | 연타 성공(기대 100) | 동시 출금 성공(기대 300) |
  |---|---|---|---|---|---|
  | main(현재) | 0원 | 0건 | 0개 | 100 | 300 |
  | 잠금 없음(기준선) | **+21,583,000~+22,027,000원 ✗** | **226~242건 ✗** | 0개 | 326~342 | 976~983 |
  | FOR UPDATE | 0원 | 0건 | 0개 | 100 | 300 |
  | @Version | 0원 | 0건 | 0개 | 100 | 264~268 |

  | 방식 | 연타 요청/초 | 연타 p95 | 동시 출금 요청/초 | 동시 출금 p95 |
  |---|---|---|---|---|
  | main(현재) | 110.5~115.3 | 1,191~1,284ms | 25.3~29.4 | 1,928~2,550ms |
  | 잠금 없음 | 63.0~67.3 | 2,258~2,375ms | 27.7~30.1 | 1,936~2,161ms |
  | FOR UPDATE | 111.4~122.2 | 945~1,147ms | 27.3~28.9 | 1,804~2,493ms |
  | @Version | 54.9~63.7 | 2,309~2,950ms | 26.4~29.3 | 2,240~2,449ms |

  요청/초는 거절된 확정도 센 값이고, p95는 동시 200건이 한꺼번에 들어가 대기가 포함된 값이다.
- **main은 3회 모두 위반 0건**이고 성공이 기대 수(1건·3건)와 정확히 같다. 명시적인 락 없이 DB가 한 문장씩 원자적으로 처리해서 중복과 초과 출금이 생기지 않는다.
- **잠금 없음**은 같은 요청ID가 약 3.3배(326~342건) 확정되고, 동시 출금도 기대의 3.3배(976~983건)가 나가서 전체 잔액이 2,158만~2,203만 원 늘었다(보내는 쪽은 마지막 쓰기만 남고 받는 쪽은 전부 반영돼 돈이 생긴다). 음수 잔액이 0개인 것은 이 변형이 읽은 잔액으로 검사한 뒤 그 값에서 빼서 쓰기 때문이다. 마이너스 대신 돈이 늘어난다.
- **FOR UPDATE**는 위반 0건이고 처리량도 main과 같은 범위다(연타 111.4~122.2 vs 110.5~115.3, 동시 출금 27.3~28.9 vs 25.3~29.4).
- **@Version**은 위반 0건이지만 충돌을 재시도 없이 거절해서, 같은 계좌 동시 출금에서 기대 300건 중 264~268건(88~89%)만 성공했다. 정상 요청 32~36건이 충돌로 거절된 것이다. 충돌은 모두 HTTP 500으로 나가서, 원래 409여야 할 중복·잔액 부족 요청도 500이 된다(5xx: 연타 206~284건, 동시 출금 686~705건). 첫 실행의 서버 로그에서 5xx 918건이 모두 `ObjectOptimisticLockingFailureException`이었다.
- **처리량 차이는 잠금 비용이 아니라 BCrypt(계좌 비밀번호 확인) 횟수와 맞아떨어진다.** 모든 방식이 잔액 확인 전에 BCrypt를 먼저 해서, 동시 출금은 요청 1,000건이 전부 BCrypt를 한 번씩 하고 방식과 상관없이 25~30 요청/초에서 같다(29 요청/초 × BCrypt p50 약 76ms(위 로그인 측정) ≈ 2.2코어 분량이라 앱에 준 2 vCPU가 BCrypt로 거의 찬 속도다). 연타에서는 main·FOR UPDATE가 중복 9개를 BCrypt 전에 돌려보내 BCrypt가 100번이고, 잠금 없음(326~342번)과 @Version(성공 100 + 충돌 206~284번)은 3~4배라 요청/초가 40~50% 줄었다.
- **한계**: 방식마다 3회이고 개발 머신(Docker Desktop)이라 절대값보다 방식 간 차이를 본다. 위반 건수는 경합 정도(DB 연결 풀 기본 10개, 동시 200건)에 따라 달라지는 값이고, 의미는 0이냐 아니냐다. BCrypt가 처리량을 지배해서 잠금 자체의 비용은 이 측정에서 보이지 않는다. 잠금 없음은 읽고-쓰는 구조라 음수 잔액이 안 나오고, 읽고-검사하고-무조건 차감하는 구조는 재지 않았다. 양방향 동시 송금(A→B와 B→A)의 교착은 범위 밖이다(main은 계좌 ID 순서로 갱신해 막고 있고, FOR UPDATE 변형은 이 순서를 지키지 않으며 이 경우는 쟀지 않았다).

**알림 추가 후 재측정**(FR-024, 2026-10-23) — 송금 확정 트랜잭션에 알림 2행 쓰기가 늘어서 같은 도구로 다시 쟀다. **측정만 하고 개선은 하지 않았다.**

- **방법**: main 방식을 알림 추가 전(`bfd8162`)과 후(FR-024 브랜치) 코드로 번갈아 3번씩 쟀다(같은 도구·시나리오·환경, 전·후 코드를 각각 따로 빌드). 판정 SQL에 알림 행 수를 더했다(main 방식에서만 — 비교용 변형은 알림을 저장하지 않는 옛 확정 구현이다): 확정된 송금 × 2 − 알림 행 수 = 0. 시나리오의 송금은 모두 서로 다른 회원 사이라 송금마다 2행이다.
- **결과**:

  | 코드 | 위반 3종(잔액 합계 차이·중복 확정·음수 잔액) | 알림 행 수 차이 | 연타 성공(기대 100) | 동시 출금 성공(기대 300) |
  |---|---|---|---|---|
  | 알림 전 | 3회 모두 0·0·0 | - | 100 | 300 |
  | 알림 후 | 3회 모두 0·0·0 | 3회 모두 0 | 100 | 300 |

  | 코드 | 연타 요청/초 | 연타 p95 | 동시 출금 요청/초 | 동시 출금 p95 |
  |---|---|---|---|---|
  | 알림 전 | 115.3~119.0 | 1,025~1,034ms | 27.2~30.0 | 2,078~2,271ms |
  | 알림 후 | 114.2~121.5 | 920~1,097ms | 28.3~29.5 | 2,169~2,458ms |

- **정합성은 그대로다**: 6회 모두 위반 0건이고 성공이 기대 수와 같다. 알림 후 3회는 확정된 송금(회당 400건)마다 알림이 정확히 2행이고(800행, 차이 0), 확정이 거절된 요청(회당 1,600건: 이미 확정·잔액 부족)에는 알림이 없다.
- **처리량·지연은 범위가 겹친다**: 연타 요청/초와 p95는 구분되지 않는다. 동시 출금 p95는 3회 평균으로 2,162ms → 2,305ms(+143ms, +6.6%)로 조금 높게 나왔지만 범위가 겹치고 3회라 차이로 보지 않는다. 처리량은 앞의 설명대로 BCrypt(계좌 비밀번호 확인)가 정한다.
- **한계**: 방식당 3회이고 개발 머신(Docker Desktop)이다. 접속 중인 연결이 없어서 저장만 잰 것이고 전달 비용은 재지 않았다. 알림이 확정 p95를 늘리는지와 대량 전달은 7절 NFR-045(추후)에서 본다.

### E2E 테스트(JSP 화면)

- **도구**: Playwright for Java. 서버(Java/Gradle)·AI(Python) 둘뿐인 프로젝트에
  세 번째 언어 툴체인(Cypress 등)을 또 들이지 않는다 — 기존 JUnit 5 테스트와
  같은 언어·같은 명령(`./gradlew test`)으로 돈다. 브라우저 바이너리를 자동
  설치해서 별도 드라이버 관리가 거의 없다(Selenium 대비 장점).
- **실행 방식**: `@SpringBootTest(webEnvironment = RANDOM_PORT)`로 실제
  서버를 띄우고, 기존 `TestcontainersConfiguration`(PostgreSQL)을 그대로
  재사용해 Playwright가 그 포트에 브라우저로 접속한다. 새 인프라를 안 만들고
  이미 있는 테스트 기반 위에 얹는다.
- **범위**: 화면(JSP)이 있는 기능마다 만든다. 지금은 회원가입 → 로그인,
  계좌 개설·충전·대표 변경, 송금 내역(무한 스크롤), 별칭 등록·목록, 채팅 송금
  (메시지 → 확인 카드 → 비밀번호 → [보내기]), 채팅 대화 유지(메뉴를 다녀와도·
  [새 대화]), 로그아웃, AI 사용량 관리(관리자 정지·해제)다. 채팅의 AI 자리는 가짜
  FastAPI로 대체하고, 확인 카드의 요청ID와 송금·잔액은 실제 Spring·PostgreSQL로
  확인한다. 화면이 없는 기능은 API 통합 테스트로 충분하고, 화면이 생기는
  시점에 그 이슈에서 E2E도 같이 추가한다(AGENTS.md 참고).

#### 알림 대량 전달(NFR-045)

| 육하원칙 | 내용 |
|---|---|
| 누가 | 같은 1초에 송금한 100만 명과 그 상대(알림 200만 건) |
| 언제 | 확정이 한꺼번에 몰릴 때(월급날·이벤트) |
| 어디서 | 알림 행 → 발송기 → 브로커 → 알림 게이트웨이 여러 대 → 브라우저(SSE) |
| 무엇을 | 확정부터 도착까지 p95 1초(접속 중인 사용자) |
| 왜 | MVP(4절)는 서버 1대가 메모리에 연결을 들고 있어 그 한 대의 연결 수·초당 전달 수가 상한이다 |
| 어떻게 | 아래 |

- **목표를 이렇게 잡은 이유**: 알림은 송금보다 먼저 나갈 수 없으니 "확정부터 도착까지"를 잰다. 1대에서 동시 접속을 1천 → 1만으로 늘려 노드 하나의 한계(연결 수, 초당 전달 수)를 재고, 100만은 노드 수로 역산한다.
- **노드가 여럿이면** 알림 행을 outbox로 읽어 브로커(Kafka 등, 사용자 ID로 파티션)에 넣고, 알림 게이트웨이 여러 대가 사용자 ID 해시로 연결을 나눠 가진다. 발송은 최소 한 번이고 `(송금 ID, 받는 사람)` 유일 키로 화면에는 한 번만 보인다.
- **알림 발송이 확정을 늦추지 않는지**도 같이 본다(확정 p95 전후 비교).
- **외부 푸시는 1초 목표에 넣지 않는다.** FCM 기본 한도가 프로젝트당 분당 60만 건이라 200만 건이면 3분이 넘는다. 접속 중인 사용자(SSE)만 1초를 약속하고, 나머지는 늦게 받는 것으로 나눈다.

#### 송금 내역 추이 그래프(FR-028·NFR-046)

| 육하원칙 | 내용 |
|---|---|
| 누가 | 내역이 많은 장기 이용자. 집계는 Spring이 SQL로 한다(LLM 아님) |
| 언제 | 내역 화면에서 기간(일·월 단위, 1개월~전체)을 고를 때 |
| 어디서 | Spring → PostgreSQL `transfer` |
| 무엇을 | 기간별 보낸·받은 금액 추이 그래프 |
| 왜 | 목록(커서 20건씩)으로는 장기 추이를 못 본다. 내역 100만 건 계정에서도 p95 < 500ms |
| 어떻게 | 아래 표를 위에서부터 하나씩, 측정으로 모자랄 때만 다음으로 |

| 선택지 | 얻는 것 | 대가 | 판단 |
|---|---|---|---|
| `(계좌, created_at)` 복합 인덱스 + `amount` 포함 | 고른 기간의 행만, 표를 읽지 않고 인덱스만 읽는다 | 기간 안의 행 수만큼은 읽는다. 쓰기마다 인덱스 갱신 | 먼저 잰다. 지금 목록 인덱스는 `(계좌, id)`다 |
| 일별 요약 테이블 | 그래프는 하루 한 행만 읽는다(10년이 약 3,650행) | 확정 때 함께 갱신하거나 밤 배치. 원본 합계와 대사가 필요 | 원본 집계가 기준을 넘으면 |
| 월 단위 파티셔닝 | 지난 달을 건너뛰고, 보관·삭제가 쉽다 | 유일 키에 파티션 키가 들어가야 하고 파티션 관리가 생긴다 | 테이블 전체가 수억 행일 때 |
| 읽기 복제본 | 조회 부하를 원본 DB에서 뗀다 | 복제 지연(방금 보낸 송금이 안 보일 수 있다), 서버 한 대 | 조회가 쓰기를 방해할 때 |
| 샤딩 | 쓰기까지 나눈다 | 두 계좌가 다른 샤드면 송금 하나를 한 트랜잭션으로 못 묶는다 | 하지 않는다. 100만 건은 PostgreSQL 한 대로 충분하다 |

- **느린 쿼리 찾기**: `pg_stat_statements`(누적 시간 상위 문장), `log_min_duration_statement`(기준을 넘는 문장 로그), `EXPLAIN (ANALYZE, BUFFERS)`(실행 계획과 읽은 블록).
- **측정**: NFR-030의 시드(다른 송금 사이에 흩어 넣은 100만 건 계정)와 같은 방식으로 기간 1개월·1년·전체의 p95를 잰다.

#### 예약 송금과 외부 연동 장애·배치 지연(FR-029·NFR-048)

| 육하원칙 | 내용 |
|---|---|
| 누가 | 규칙을 만드는 사용자(채팅·MCP로 초안 → 확인 카드에서 계좌 비밀번호로 등록). 실행은 Spring 스케줄러 |
| 언제 | 규칙의 날짜·시각(예: 매월 25일 09:00). 같은 시각에 규칙이 몰린다 |
| 어디서 | 스케줄러 → 원장(같은 DB). 타행 송금을 넣으면 외부 이체망(가짜 서버로 흉내) |
| 무엇을 | 정해진 날 자동 송금과 결과 알림(FR-024) |
| 왜 | 반복 송금을 매번 채팅으로 하지 않게 한다. 외부 API 장애와 배치 지연을 송금 도메인에서 다룬다 |
| 어떻게 | 아래 표 |

| 상황 | 문제 | 대응 |
|---|---|---|
| 25일 09:00에 규칙 수만 건이 한꺼번에 돈다 | 처리가 밀려 "아직 안 나갔다"가 보이고, 그사이 잔액을 써서 실패한다 | 실행 시각을 몇 분 안에 흩고, 워커 여러 개가 `FOR UPDATE SKIP LOCKED`로 나눠 가진다. 상태(예정 → 처리 중 → 완료·실패·확인 필요)와 남은 건수를 그대로 보여 준다 |
| 서버가 실행 중에 재시작한다 | 같은 규칙이 두 번 돌거나 빠진다 | `(규칙 ID, 실행일)` 유일 키로 한 번만 실행한다(지금 요청ID 1회용과 같은 방식) |
| 외부 이체망이 응답 없이 끊긴다(타임아웃) | 돈이 갔는지 모른다. 다시 보내면 두 번 나간다 | 다시 보내지 않고 우리 거래 ID로 조회해 확인한다. 확인 전에는 '확인 필요' |
| 외부 이체망 점검·장애가 길다 | 실패가 쌓이고 재시도가 장애를 키운다 | 일시 오류(5xx·429·타임아웃)만 지수 백오프 + 지터로 재시도하고, 연속 실패면 차단기로 멈췄다가 회복 뒤 순서대로 보낸다. 영구 오류(계좌 없음)는 바로 실패·알림 |

- **하루 마감 대사**: NFR-034의 SQL 3개(전체 잔액 합계 불변·중복 확정 0·음수 잔액 0)에 외부 이체망 결과와 우리 기록 비교를 더한다.
- **지금 있는 외부 API에도 같은 분류를 쓴다.** 지금 DART 오류는 종류 구분 없이 하나(`DartError`, '데이터 없음'만 따로)다. 사업의 내용은 회사 단위로 실패를 격리하고 다음 날 다시 시도하지만, 재무 수집에서 DART 오류가 하나 나면 그날 수집(사업의 내용 포함) 전체가 멈추고 24시간 뒤에 다시 돈다. 일시 오류는 몇 분 뒤 재시도, 한도 초과·점검은 다음 주기로 나눈다. 채팅 LLM은 같은 곳으로 재시도하지 않고, 대체 공급자로 한 번만 넘긴다(NFR-056, 읽기 제한 10초 안에 끝나야 한다). 사업의 내용 재검색(NFR-052)은 오류 재시도가 아니라 근거 없는 숫자에 대한 답변 품질 루프다.

#### AI 시나리오 테스트(NFR-047)

| 육하원칙 | 내용 |
|---|---|
| 누가 | 사용자 역할을 하는 LLM(처음 쓰는 사람, 급한 사람, 오타·줄임말, 중간에 말을 바꾸는 사람) |
| 언제 | 프롬프트·모델·가드를 바꾼 뒤, 배포 전 |
| 어디서 | 실제 API와 실제 OpenAI(로컬 실데이터). 화면 확인이 필요하면 Playwright E2E 위에서 |
| 무엇을 | 대화 시나리오를 만들어 끝까지 진행하고, UX를 해치는 대화를 골라낸다 |
| 왜 | 사람이 매번 채팅해 보지 않아도 되묻기 반복, 엉뚱한 확인 카드, 느린 답을 찾는다 |
| 어떻게 | 아래 |

- **합격은 규칙으로 판정한다**: 틀린 확인 카드 0(금액·수취인이 시나리오 정답과 일치), 턴 응답이 읽기 제한(10초) 안, 같은 내용 되묻기 2회 이하, 내부 오류 문구 노출 0. 판정을 LLM에게 맡기지 않는 원칙(5절) 그대로다.
- **LLM 판정은 후보 표시만 한다**: 답이 질문과 어긋나거나 말투가 어색한 대화에 점수를 남기고, 점수가 낮은 대화만 사람이 읽는다.
- **비용·반복**: 시나리오 × 턴만큼 실제 호출이라 실행 전 예상 비용을 적고(NFR-035와 같은 방식), 같은 세트를 3번 돌려 범위를 적는다.

#### 수평 확장·급증 대응(NFR-049)

| 육하원칙 | 내용 |
|---|---|
| 누가 | 사람 사용자, 3단계(MCP) 뒤에는 에이전트 |
| 언제 | 피크 30분 사용자가 약 4,800명(1대 한계 15 TPS × 1,800초 ÷ 세션당 요청 5.65)을 넘을 때, 에이전트 호출이 몰릴 때 |
| 어디서 | 앞단(nginx) → Spring 여러 대 → FastAPI 여러 대 → PostgreSQL 한 대(+ 커넥션 풀러) |
| 무엇을 | 넘치는 요청을 먼저 막고(입장 제어), 그다음 대수를 늘린다 |
| 왜 | 1대는 평균 피크도 못 버틴다(6절 역산). 막지 않으면 모두가 느려진다(652 TPS: 일반 API p95 60초, 실패 36%) |
| 어떻게 | 아래 순서로 하나씩, 단계마다 같은 `stress.sh`로 한계 TPS를 비교한다 |

1. **입장 제어**: 사용자·API 키별 한도(NFR-024를 키별로), 동시 처리 상한, 대기열이 차면 기다리게 두지 않고 429 + `Retry-After`. 송금 확정은 채팅보다 먼저 받는다. 에이전트는 실패하면 바로 재시도하므로 쓰기 도구는 멱등 키를 받는다.
2. **무상태로 만든다**: 대화 상태는 PostgreSQL 체크포인터(FR-015)로, 호출 제한 카운터·캐시는 Redis(NFR-025, 2절 4단계)로. JWT는 이미 서버에 상태가 없다. 알림 SSE 연결은 서버마다 따로라 Redis pub/sub으로 어느 서버에 붙은 사람에게든 닿게 한다(4절).
3. **대수를 늘린다**: 먼저 무너지는 FastAPI부터. 이미 있는 nginx(NFR-053)에 대상 서버를 더하고, DB 커넥션 합이 `max_connections`를 넘지 않게 PgBouncer를 둔다.
4. **LLM 한도**: OpenAI 계정 한도(분당 토큰·요청)가 전체 상한이라 우리 쪽에서 토큰 예산을 세고, 넘치면 대기열 대신 거절한다. 사용자별 하루 한도는 MVP에 있다(NFR-054).

- **측정**: 1 → 2 → 4대에서 한계 TPS가 대수만큼 오르는지, 다음 병목(DB 커넥션·락)이 어디인지 잰다(가짜 LLM).

#### 홈서버 망 분리·접근 통제(NFR-050)

- **VPC 이해 확인**: public 서브넷에는 밖에서 오는 요청을 받는 것(로드밸런서·nginx)과 NAT 게이트웨이만 두고 앱·DB는 private에 둔다 — 맞다. 다만 OpenAI 같은 외부 호출은 public에 따로 두는 것이 아니라 private의 앱이 NAT를 거쳐 밖으로 나간다(밖에서 private로는 못 들어온다). "오래 걸리는 외부 호출을 따로 뺀다"는 망 구분이 아니라 작업 격리이고, SMART에서는 FastAPI를 따로 둔 것이 그것이다(1절 장애 격리).

| 육하원칙 | 내용 |
|---|---|
| 누가 | 밖의 사용자(웹), 관리자(SSH·Grafana·DB), 배포(GitHub Actions) |
| 언제 | 웹을 인터넷에 공개하기 전, AWS로 옮기기 전 |
| 어디서 | 홈서버 한 대: 공유기, 호스트 방화벽, Docker 네트워크 |
| 무엇을 | 공개 망과 내부 망을 나누고, 들어오는 길을 터널 하나로 줄인다 |
| 왜 | 지금은 배포용 SSH(2222)가 공유기 포트포워딩으로 인터넷에 열려 있고, Spring 8080은 호스트의 모든 인터페이스에 열려 있다(DB는 127.0.0.1에만, 8080은 MVP nginx에서 닫는다) |
| 어떻게 | 아래 그림과 표 |

```text
인터넷 ─터널(서버가 밖으로 연결, 들어오는 포트 0)─▶ [터널 커넥터] ─edge(internal)─▶ [nginx] ─▶ [Spring]
[Spring] ─app(internal)─▶ [FastAPI]·[DB]            internal 망은 인터넷으로 못 나간다
[터널 커넥터]·[FastAPI]·[collector] ─egress─▶ 인터넷(Cloudflare·OpenAI·DART)
관리자·배포 ─Tailscale(사람·기기 확인)─▶ SSH·Grafana·DB
```

| 방법 | 막는 것 | 대가 | 판단 |
|---|---|---|---|
| 포트포워딩 + 호스트 방화벽(ufw·nftables) | 열어 둔 포트 밖 전부 | 집 공인 IP가 드러나고 열린 포트는 인터넷 전체가 두드린다. Docker가 연 포트는 ufw 규칙을 건너뛴다 | 기본으로 깔되 이것만으로 끝내지 않는다. MVP는 80·443만 nginx로 연다(NFR-053) |
| Cloudflare Tunnel(+ Access) | 들어오는 포트 0개(서버가 밖으로 연결). IP를 숨기고 TLS·DDoS를 앞단이 맡는다 | 외부 업체에 기대고, TLS가 그 업체에서 풀린다 | 웹 공개용 |
| Tailscale(WireGuard) | 관리 접속을 사람·기기 단위로만 허용(ACL) | 접속하는 기기마다 앱 설치 | 관리·배포용. 배포는 Actions가 임시 노드로 붙어 SSH |
| 서비스 간 mTLS·서비스 메시 | 내부 망 안의 도청·사칭 | 인증서 운영. 컨테이너 몇 개짜리 한 대에는 과하다 | 하지 않는다. 망 분리 + 사용자 JWT 전달(NFR-006)로 대신 |

- **추천안**: 위의 세 가지를 함께 쓴다. 웹은 터널로만, 관리·배포는 Tailscale로만 받고(공유기 포트포워딩 제거), 호스트는 들어오는 연결을 기본 차단하고, Docker 포트는 `127.0.0.1:`에만 연다.
- **제로트러스트로 보면**: 망 위치로 믿지 않는다. 사용자 요청은 매번 JWT를 확인하고(지금), 관리 접속은 사람·기기를 확인하고(Tailscale·Access), DB 계정은 앱별로 나눠 최소 권한만 주고(지금은 계정 하나), 접속 기록을 남긴다.

#### 홈서버 운영 점검(NFR-051)

| 육하원칙 | 내용 |
|---|---|
| 누가 | 운영자 |
| 언제 | 공개 전 한 번, 그 뒤 분기마다 |
| 어디서 | 공유기·OS·Docker·PostgreSQL |
| 무엇을 | 아래 네 층의 점검표 |
| 왜 | 클라우드가 대신해 주던 것(공인 IP, 백업, 보안 패치, 전원)을 직접 챙겨야 한다 |
| 어떻게 | 아래 표 |

| 층 | 점검 | 놓치면 |
|---|---|---|
| 네트워크 | 공유기 WAN IP가 공인 IP인지(CGNAT면 포트포워딩 불가 → 터널), 유동 IP(DDNS·터널), 업로드 대역폭, ISP 약관(서버 운영·포트 차단) | 밖에서 아예 닿지 않거나, IP가 바뀌면 끊긴다 |
| 미들웨어 | 타임아웃 사슬(앞단 > Spring 읽기 제한 10초·상세 30초 > LLM), 컨테이너 로그 크기 제한, 재시작 정책·헬스체크 | 앞단이 먼저 끊으면 끝난 일이 실패로 보인다. 로그가 디스크를 채운다 |
| OS | 보안 업데이트 자동, 시간 동기(NTP), 디스크·메모리 경고, SSH 키 전용(비밀번호 로그인 끔), 재부팅 뒤 Docker 자동 시작 | 시계가 틀리면 JWT 만료·예약 송금·수집 시각이 틀린다 |
| DB | 매일 백업 + 다른 곳에 보관 + 복구 리허설, 커넥션 합(Spring 풀 + FastAPI + collector) ≤ `max_connections`, 슬로우 쿼리 로그, 디스크 여유 | 지금은 백업 절차 없이 Docker 볼륨 하나에 원장 전체가 있다 |

## 8. 기술 스택

| 구분 | 기술 |
|---|---|
| 화면 | JSP (로그인·회원가입, 채팅, 계좌·충전, 송금 내역, 별칭) + 공통 CSS(현대닷컴 톤) |
| 백엔드 | Spring Boot 4.1.1, Java 17, JPA, JWT. FastAPI 호출: RestClient(1단계) → WebClient(2단계) |
| AI | FastAPI, LangGraph, OpenAI(LLM·임베딩), Claude(LLM 장애 대체) |
| DB | PostgreSQL 하나 (회원·계좌·송금·알림 + AI 사용량 + 재무 테이블 + pgvector) |
| 배포 | Docker Compose로 로컬 실행(Spring Boot·FastAPI 모두). 홈서버: 앞단 nginx(도메인 HTTPS), `main` 머지 시 GitHub Actions가 이미지를 빌드해 Docker Hub에 올리고 SSH로 pull·재실행 → 추후 AWS EC2 |
| 테스트·모니터링 | k6(Prometheus remote write), Prometheus(Spring Actuator·FastAPI·postgres_exporter·cAdvisor), Grafana |

### 쓰지 않는 기술과 도입 조건

기술은 필요할 때 도입하고 근거를 남긴다(1절). 지금 쓰지 않는 이유와 도입 트리거를 적어 둔다.

| 기술 | 지금 쓰지 않는 이유 | 도입 조건 | 도입하면 잴 것 |
|---|---|---|---|
| **Redis** | 캐시할 만한 곳은 LLM 호출이 지연의 대부분(2~7초)이라 저장소가 ms 단위인지는 문제가 아니다. 지금은 인스턴스 1대·FastAPI 워커 1개라 프로세스 내 캐시와 메모리 카운터로 충분하다. 컨테이너가 하나 늘면 t3.small(2GiB) 한도 안에서 JVM·PostgreSQL·FastAPI와 메모리를 나눠 쓰고, 운영 대상(장애·보안)도 늘어난다 | 2절 4단계의 (a)~(c): 인스턴스 2대 이상, 재시작 때 캐시 손실, 프로세스 메모리 초과 | 히트율, p50·p95, LLM 호출 수, 1천 채팅당 비용 |
| **별도 AI 게이트웨이**(LiteLLM 등) | LLM 호출이 이미 FastAPI의 LLM 객체 하나를 지나서 감쌀 곳이 하나다. 컨테이너가 하나 늘고 호출마다 한 홉이 더해지며, 사용자별 기록에는 결국 우리 회원 ID가 필요하다(5절) | 여러 서비스가 LLM 키를 나눠 쓸 때, 공급자가 셋 이상이라 라우팅을 코드 대신 설정으로 바꾸고 싶을 때 | 호출당 추가 지연, 옮긴 뒤 줄어든 코드 |

## 9. 아키텍처 / 흐름

### 전체 구성

```text
[JSP] ◀─HTTPS─▶ [nginx] ◀──▶ [Spring Boot] ◀──내부 REST──▶ [FastAPI + LangGraph] ─AI 게이트웨이─▶ OpenAI(장애 시 Claude)
                                   │                               │
                                   ▼                               ▼
          [PostgreSQL: 회원·계좌·송금·알림 | AI 사용량 | 재무 테이블 | pgvector(사업의 내용)] ◀── [FastAPI 스케줄러]
```

- 알림 스트림(SSE)도 같은 길(nginx → Spring)로 온다.

### LangGraph 워크플로우 (큰 흐름)

```text
사용자 메시지
   ▼
[의도 분류]
   ├─ 송금   ──▶ Spring 송금 요청 생성 ──▶ 확인 카드 반환
   ├─ 내역   ──▶ Spring 내역 조회 ──▶ 설명
   └─ DART   ──┬─ 재무 테이블 ──▶ 계산 코드(수치·경쟁사 비교) ──▶ 요약 + 표
               └─ pgvector 검색(사업의 내용) ──▶ 요약 ──▶ [출력 가드]
                        ▲                        │ 근거 없는 숫자(턴마다 1회)
                        └──── 질문 고쳐 쓰기 ◀───┘
```

### 채팅 송금

```text
JSP ─"엄마한테 1만원"─▶ Spring ─▶ FastAPI(LangGraph) ─송금 요청 생성─▶ Spring
                                                      (요청ID 발급, 금액·수취인 고정 저장)
JSP ◀──────────────── 확인 카드(요청ID) ────────────────────────────────┘
JSP [보내기] ─요청ID + 계좌 비밀번호─▶ Spring: 본인 확인 → 비밀번호 확인 → 트랜잭션(잔액 차감·입금·내역 기록·알림 2건)
JSP(보낸 사람·받은 사람) ◀──── SSE 알림(커밋 뒤, 접속 중일 때) ──── Spring
```

### DART 수집

```text
[매일] FastAPI 스케줄러 전용 컨테이너(collector)
       다중회사 주요계정 API(최근 2년 8개 기간) ─▶ 재무 테이블
       공시서류원본파일 API ─▶ "사업의 내용" 추출 ─▶ 청킹 ─▶ OpenAI 임베딩 ─▶ pgvector
       (정정본은 덮어쓰기, 사업의 내용은 회사별 최신 보고서만)
```
