# SMART 종합 개요

AI 채팅으로 송금하고, DART 공시를 검색·분석하는 서비스.

| 글자 | 영역 | 내용 |
|---|---|---|
| **S** | Sending | 송금 |
| **M** | Management | 송금 내역 조회 |
| **A** | AI & Analysis | LangGraph 기반 AI 분석 |
| **R** | RAG & Retrieval | DART 공시 데이터 검색·RAG |
| **T** | Transfer | 공시 데이터 전송·송금 업무 |

---

## 1. 목적 / 개발 관점

- **기능을 늘리기보다, 핵심 기능마다 꼬리 질문 5개에 답할 수 있는 포트폴리오를 만든다.**
  - 예: Redis 캐시를 쓴다면 왜 로컬 캐시가 아닌 Redis인지, TTL은 왜 그 값인지, 응답·부하 속도를 개선하려고 무엇을 했는지
- 포트폴리오이자 개발 기준 문서다.

### 심화 주제

| 주제 | 꼬리 질문 대비 범위 |
|---|---|
| **AI 송금 안전장치** | 금액·수취인 오인식 / 확인 버튼 우회 방지 / 중복 클릭·재시도 / 동시 송금 시 잔액 정합성 |
| **RAG 검색 품질** | 평가셋으로 수치 측정 / 청킹·검색 방식 비교 / 재무 수치 환각 방지 |

### 서버를 둘로 나눈 이유: 장애 격리

- LLM 응답이 느리거나 FastAPI에 장애가 나도 송금·계좌 기능은 정상 동작하도록 AI 기능을 별도 서버로 분리했다.
- 파이썬 AI 생태계를 그대로 쓰고, AI 서버만 따로 확장할 수 있다.

### 원칙

- **기술 도입**: Redis 같은 기술은 필요할 때 도입하고, 도입 이유를 근거로 남긴다.
- **결정 근거 기록**: 개요에는 원칙만 적고, 상세한 근거는 별도 문서에 둔다.
- **성능 측정**: 트래픽을 추정해 목표를 정하고, k6 + Prometheus + Grafana로 성능·부하·정합성을 측정한다(6절).
- **범위**: 핵심 기능 외 디테일은 개발과 문서 모두에서 뺀다.
  - 제외: CSRF 방어, 페이지 보호(비로그인 차단), 입력값 검증·공통 예외 처리
  - 화면 스타일은 현대닷컴(hyundai.com/kr/ko/e) 톤의 공통 CSS(`static/css/smart.css`) 하나만 둔다. 화면별 디자인·컴포넌트 라이브러리는 만들지 않고, 폰트·로고·이미지는 쓰지 않는다. Vue PWA로 옮길 때 이 CSS의 토큰을 그대로 가져간다.
  - 남김(송금 안전장치와 연결): 계좌 소유자 확인, 비밀번호 해시 저장

## 2. 단계별 로드맵

단계마다 **하나씩만** 바꿔서, 각 변경의 효과를 수치로 따로 설명한다.

| 단계 | 내용 | 근거·측정 |
|---|---|---|
| **1단계 (하루 MVP)** | Spring ↔ FastAPI 내부 REST 연동, Spring은 RestClient | 기준 수치. LLM을 기다리는 동안 Spring 스레드가 묶임 |
| **2단계** | 비동기 전환(WebClient) | Java 17이라 가상 스레드를 쓸 수 없음 → LLM 대기 중 스레드 반납, 동시 처리량 비교 |
| **3단계** | MCP 서버 제작·적용 | 송금·계좌 도구(조회·송금 요청 생성까지, 실행 권한 없음), DART 검색 도구 |
| **4단계** | 캐싱(성능 개선) | 자주 묻는 질문에서 LLM 호출을 건너뛴다 → 히트율·p95·LLM 호출 수·비용을 캐시 없음과 비교 |

- Spring ↔ FastAPI 구간은 REST(WebClient)까지만 간다. gRPC는 도입하지 않는다.

### 4단계 캐싱 설계

**LLM 호출 앞에 둔다.** 지연과 비용의 대부분이 LLM 호출이다(5절 실측: 의도 추출 2.3~2.5초, 사업의 내용 답변 6.9초, 재무 조회 29ms). 캐시 적중은 초 단위를 아끼고 저장소 조회는 ms 단위라, 저장소가 로컬이냐 Redis냐의 속도 차이는 선택 기준이 아니다.

**먼저 재고 정한다.** 정규화한 질문의 해시를 로그에 남겨(본문은 남기지 않는다) 상위 질문이 전체에서 차지하는 비율, 곧 히트율 상한을 잰다. 반복이 없으면 도입하지 않는다.

| 대상 | 종류 | 키 | 무효화·TTL | 건너뛰는 것 |
|---|---|---|---|---|
| ① 의도 추출 결과 | 함수 결과 메모이제이션(정확 일치) | 모델·프롬프트·가드 버전 + 가린 질문(정규화) + 진행 중 송금 값 | 버전이 바뀌면 키가 바뀐다. TTL 24시간 | 의도 추출 LLM 2.3~2.5초. 모든 질문 |
| ② 사업의 내용 답변 | 응답 캐시(사용자 간 공유) | 종목코드 + 회사별 최신 접수번호 + 정규화한 질문(새 대화의 첫 질문만) | 새 보고서가 오면 접수번호가 바뀌어 키가 바뀐다. TTL 24시간 | 임베딩·검색·답변 LLM 약 7초 |
| ③ 상세 보기 보고서 | 응답 캐시(공유) | 분석 조건(기업·기간·기준) + 데이터 버전 | 데이터 버전이 바뀌면 키가 바뀐다 | 보고서 생성 LLM. 상세 보기(FR-016) 구현 뒤 |

- **TTL 24시간**: 수집이 하루 1회라 그 안에서는 원천 데이터가 바뀌지 않는다. 새 보고서는 접수번호로 키가 바뀌므로 TTL은 정확성이 아니라 메모리 상한을 위한 값이다.
- **정확 일치만 쓴다.** 의미 유사도(시맨틱) 캐시는 쓰지 않는다. '삼성전자 영업이익'과 '삼성SDI 영업이익'은 임베딩이 가깝지만 답이 다르고, 틀린 답을 내보내는 비용이 느린 응답보다 크다.
- **가드를 통과한 답변만 저장한다.** 걸린 답변·오류 안내는 저장하지 않는다. 가드 규칙·프롬프트가 바뀌면 버전이 키에 들어 있어 이전 항목은 쓰이지 않는다.
- **돈과 사용자 데이터는 캐시하지 않는다.** 잔액·송금 요청·확정·내역은 사용자별이고 정합성이 돈과 직결된다(NFR-009·010). 재무 비교 표도 하지 않는다. 코드가 29ms에 계산해서 건너뛸 것이 없고 항상 최신 수집분이다. 그 질문에서 느린 부분(의도 추출)은 ①이 건너뛴다.
- **대화 맥락이 답에 영향을 주므로** ②는 이전 대화가 없는 첫 질문에만 쓴다. 주민·카드번호를 가린 문장이 든 질문은 공유 캐시에 넣지 않는다.
- **하지 않는 것**: 일반 답변(잡담)은 재사용 가치가 낮다. 질문 임베딩 캐시는 ②가 빗나갔을 때만 이득이라(0.2~1.5초) 하지 않는다. OpenAI 프롬프트 캐시는 앞부분이 같은 긴 프롬프트(1,024토큰 이상)에만 듣는데, 추출 프롬프트는 짧고 사업의 내용 프롬프트는 지시문만 같고 공시 본문이 질문마다 달라 효과가 작다.

**구현은 한 번에 하나씩.**

1. **프로세스 내 캐시**(TTL + LRU, 크기 상한). 인스턴스 1대·FastAPI 워커 1개(메모리 체크포인터)라 공유 효과가 같고 인프라가 없다. 값이 작아(답변 1~2KB, 추출 결과 수백 바이트) 1만 건이 약 20MB 수준이다(추정).
2. **Redis**. 아래 중 하나가 측정이나 구성으로 확인되면 바꾼다. (a) 인스턴스가 2대 이상이라 캐시와 호출 제한 카운터(NFR-025)를 공유해야 한다. (b) 재시작·배포로 캐시를 잃는 비용이 크다. (c) 캐시가 프로세스 메모리를 넘는다.
3. 같은 질문이 TTL 만료 직후나 장 시작 직후(피크 30분)에 몰리면 같은 LLM 호출이 겹친다. 키별 락으로 한 번만 호출하고 나머지는 기다린다(single-flight).

**측정**: 캐시 없음 → 프로세스 캐시(→ Redis)를 한 번에 하나만 바꿔 비교한다. 지표는 히트율, 질문 유형별 p50·p95, LLM 호출 수, 1천 채팅당 비용이다. 질문 풀의 쏠림을 바꿔 가며 히트율별 p95를 함께 낸다. 기준 부하 테스트(NFR-031)는 캐시를 끈 상태로 둔다. 가짜 LLM은 실측 지연 분포를 그대로 쓰므로 캐시 효과는 "히트율 × LLM 지연"으로 설명된다.

## 3. 서버 역할 분담

| 서버 | 역할 |
|---|---|
| **Spring Boot** | 금융 트랜잭션·비즈니스 처리. 잔액·충전·송금·내역 합계 등 돈 관련 숫자 계산 |
| **FastAPI** (내부 전용, Spring만 호출) | 채팅·AI 분석 요청을 받아 LangGraph 에이전트 워크플로우 구동. DART 재무 수치는 파이썬 계산 코드로 계산. DART 수집 스케줄러 |

- **LLM은 숫자를 만들지 않는다.** 숫자는 코드가 계산하고, LLM은 받은 숫자를 설명만 한다(재무 수치 환각 방지의 근거).
- **AI 경로에는 송금 실행 권한이 없다.** LangGraph는 조회와 송금 요청 생성까지만 하고, 실제 송금은 사용자가 [보내기]를 누르면 Spring이 실행한다.
- **계좌 비밀번호는 채팅으로 받지 않는다.** 채팅 메시지는 OpenAI와 대화 기록에 남기 때문에, 비밀번호는 확인 카드에서만 받아 Spring이 바로 확인한다.

## 4. 핵심 기능 (1단계 MVP)

- **회원**: 회원가입·로그인(JWT). 여러 사용자가 함께 이용
  - 로그아웃은 화면이 토큰과 대화 기록을 지우고 로그인으로 보낸다. 서버에서 토큰을 무효화하지 않는다(만료 1시간).
- **계좌**: 서비스 안에서 가상계좌 개설(계좌 비밀번호 숫자 4자리), 충전 기능
- **송금**: 가상 잔액 송금(실제 돈 아님). 받은 쪽 잔액이 늘어남. 한도 없음
  - 받는 사람 지정: 계좌번호, 자주 쓰는 상대(별칭)
- **AI 채팅 송금**: 확인 카드에 계좌 비밀번호를 넣고 [보내기]를 눌러야 실행. 채팅으로 내역 조회
- **송금 내역(Management)**: 목록 조회. 1단계 안에서 전체 조회 → 오프셋 → 커서 무한 스크롤로 개선하고 단계마다 k6로 측정
- **DART 분석**: 코스피200 기업만. 사업의 내용 요약, 재무 수치 비교(경쟁사 비교 포함). 수주금액·투자금처럼 비교 지표 4개에 없는 숫자는 사업의 내용(RAG)에서 답하고 출처를 표시
- **채팅 기록**: 현재 대화 맥락만 유지(LangGraph 체크포인터 + thread_id). 대화방 목록 화면은 없음
  - MVP는 메모리 체크포인터. 워커 1개에서만 맞게 동작하고, 재시작하면 기록이 사라지며, 대화가 쌓이면 메모리가 늘어난다. 부하·재시작 테스트에서 문제가 확인되면 PostgreSQL 체크포인터로 바꾸고 전후 수치를 남긴다.
  - 기록에는 가린 문장만 남긴다(개인정보는 그래프에 넣기 전에 가림, 인젝션으로 막힌 문장은 기록 제외).
  - 화면은 `thread_id`와 말풍선·확인 카드 결과를 탭의 sessionStorage에 두어 메뉴를 옮겨도 같은 대화를 잇는다. [새 대화]로 새로 시작하고, 탭을 닫거나 로그아웃·로그인하면 비운다. 답을 기다리는 중에 메뉴를 옮기면 그 답은 화면에 남지 않는다. 서버에 저장하는 지난 대화 목록은 추후.

### 채팅 답변

- 스트리밍 없음. 채팅 답변은 요약으로 짧게 준다.
- 긴 보고서는 [상세 보기] → 팝업·새 화면. 내용은 클릭할 때 생성한다.

### DART 경쟁사 비교

| 항목 | 기준 |
|---|---|
| 경쟁사 선정 | 직접 만든 경쟁사 목록 + 사용자 지정 우선. 질문에 "경쟁"이 있고 기업을 하나만 말했을 때 그 업종의 경쟁사를 더한다. 기업을 둘 이상 말하면 말한 그대로 비교한다. 목록에 없는 기업은 사용자 지정으로만 비교하고, 직접 말해 달라고 안내한다 |
| MVP 업종 | 반도체(삼성전자·SK하이닉스), 자동차(현대차·기아·현대모비스), 2차전지(LG에너지솔루션·삼성SDI), 인터넷(NAVER·카카오). 아래 선정 근거 |
| 개수 | 한 번에 최대 3개(질문한 기업 포함). 넘으면 앞의 3곳만 비교하고 제외한 기업을 알린다 |
| 재무제표 기준 | 연결 우선, 없으면 별도. 비교 대상 모두 같은 기준으로 맞추고 어떤 기준인지 답변에 표시 |
| 기간 | 최근 분기 + 전년 동기 대비 |
| 지표 | 매출액, 영업이익, 당기순이익, 영업이익률(계산 코드가 산출) |
| 표시 | 채팅: 요약 + 표 / 상세 보기: 전체. 차트 없음 |
| 시점 차이 | 같은 분기 공시가 없는 회사는 비교에서 빼고 '미공시'로 표시 |

- **업종 선정**: 수집 대상 30곳 안에서, 모두 같은 분기(2026년 2분기)에 연결 기준 매출액·영업이익·당기순이익이 있어 지표 4개가 다 나오는 업종만 골랐다. 금융지주(KB·신한·하나·우리)와 삼성생명은 주요계정에 `매출액`이 없어 영업이익률을 만들 수 없으므로 뺐다(금융용 지표는 명세 변경이 먼저다). 통신은 LG유플러스가 수집 대상이 아니고, 바이오는 사업 모델이 다르고(위탁생산·바이오시밀러), 정유·화학은 배터리까지 섞여 있어 후순위다.
- **목록**: `ai/app/financial.py`의 `COMPETITOR_GROUPS`(종목코드 묶음). 업종을 늘릴 때 한 줄 더한다. 묶음의 기업이 모두 수집 대상인지는 테스트가 확인한다.
- **구현**: "경쟁" 여부는 질문 글자로 판단한다(의도 추출은 재무 비교인지와 기업 이름만 맡는다). 비교 대상이 정해지면 표·미공시·기준 통일은 재무 비교와 같은 코드가 만들고, 상세 보기도 경쟁사를 포함한 전체로 만든다.
- **실측**(`ai/evals/competitors.py`, 33문장 × 3회, gpt-5-nano·추론 강도 low, 로컬 실데이터 30곳, 2026-10-16): 처음 프롬프트로는 '경쟁사' 문장이 기대한 재무 비교로 이어지는 비율이 낮았다. 프롬프트를 고칠 때 본 16문장에서 39%, 따로 만든 12문장에서 47%였다. 실패는 LLM이 경쟁사 이름을 스스로 채우거나(토요타·Bosch), 기업을 영문으로 번역하거나(`Samsung SDI`), 말한 기업을 비우거나 '경쟁사'를 기업으로 넣는 경우였다. 프롬프트에 "경쟁사와 비교해 달라는 요청은 재무 비교이고, 기업은 사용자가 말한 것만 말한 그대로"와 예시 2개를 넣어 각각 99%·98%로 올랐고, 그래프를 끝까지 돌린 평가(기대한 비교 대상이 순서까지 맞는 비율)는 평균 31.7/33(96%, 범위 31~32)다. 고치는 중에 본 문장이라 낙관적일 수 있다.
- **영향 확인**: 같은 프롬프트로 기업명 인식 세트를 다시 돌려 재무 의도 100%(20/20)는 그대로이고, 기업명 인식은 같은 날 기준선 평균 11.3/20(57%, 범위 10~12)에서 10.0/20(50%, 범위 10)로 낮았다. 줄임말 '삼전'·'삼성바이오'가 3회 중 1회 실패에서 3회 모두 실패로 바뀐 차이다("말한 그대로"를 분명히 한 결과). 별칭 사전·정식명 변환은 이 세트로 따로 잰다.

## 5. AI 가드레일

**넓게는 얇게, 하나만 깊게.** 다섯 위치에 최소한으로 깔고, 숫자 환각 가드 하나만 5단계까지 판다.
라이브러리는 쓰지 않고 아이디어만 가져와 파이썬 규칙 + LangGraph 노드로 직접 구현한다.

| 위치 | MVP |
|---|---|
| 입력 | 인젝션 대표 유형 규칙(걸리면 LLM 미호출) + 주민·카드번호 가림 |
| 구조화 | 송금 금액·수취인(계좌번호·별칭)을 스키마로 검증하고 원문과 다시 대조, 빠지거나 애매하면 되묻고 같은 대화에서 이어 받기 |
| 검색 | 공시 본문을 '데이터' 구분자로 감싸서 전달 |
| 출력 | **숫자 환각 가드(깊게)**, 투자 권유 표현, 시스템 프롬프트 유출 감지(카나리 단어) |
| 실행 | 요청ID 1회용·5분 만료·본인 확인·계좌 비밀번호(틀리면 요청ID 폐기 → 새 요청은 채팅 호출 제한을 받아 비밀번호 추측이 느려짐) |

- 걸리면 정상 응답 + 고정 문장 + 판정 코드(`guard`). 가드는 LangGraph 노드이고, 걸리면 조건부 엣지로 바로 종료한다.

### 출력 가드(구현 범위)

LLM이 쓴 답변(일반 답변·사업의 내용 답변)은 출력 가드 노드를 거쳐야 나간다. 걸리면 고정 문장으로 바꾸고, 대화 기록에도 바뀐 문장만 남는다(샌 문장·믿을 수 없는 숫자가 다음 턴에 가지 않는다).

| 판정 | 방법 | 나가는 답변 |
|---|---|---|
| `PROMPT_LEAK` | 시스템 프롬프트에 심은 카나리 단어가 답변에 있는지. 카나리는 프로세스마다 새로 만든다 | 고정 문장 |
| `ADVICE` | 투자 권유 표현 목록. 공시에 나오는 말('비중 확대'·'자기주식 매수')은 넣지 않는다 | 고정 문장 |
| `NUMBER_UNVERIFIED` | 답변의 숫자가 LLM에 준 근거에 있는지(2단계). 사업의 내용 답변은 공시 블록, 상세 보고서는 표다. 질문에 쓴 숫자나 이전 답변은 근거가 아니다 | 고정 문장 + 출처(상세 보고서는 표) |

- 재무 표·요약 문장·내역·송금 확인 문장은 코드가 만들어서 가드 대상이 아니다(NFR-002). 일반 답변은 근거가 없어 숫자를 대조하지 않는다.
- 근거 텍스트(공시 블록)는 상태에 두지 않고 노드 안에서 대조한다. 체크포인터에 본문이 쌓이지 않게 하려는 것이다.
- 안전 판정을 LLM에게 맡기지 않는다. 분류 모델(Prompt Guard)은 추후 추가해 규칙만 쓸 때와 전후를 측정한다.

### 숫자 환각 가드 5단계

단계마다 평가 세트로 측정한다. 정답이 재무 테이블에 있어 자동 채점된다. 심화 주제 "재무 수치 환각 방지"의 근거다.
대조 근거는 둘로 나뉜다. 재무 지표 4개는 재무 테이블과 항목·값 쌍으로, 사업의 내용 본문 숫자(수주금액 등)는 검색 조각과 존재 대조하고 출처를 표시한다.

```text
1단계 프롬프트만        → 기준선 환각률                       (MVP)
2단계 숫자 존재 대조    → "다른 항목 숫자" 구멍 재현             (MVP)
3단계 항목·값 쌍 대조   → 구멍 해결                            (MVP)
4단계 표기 정규화       → 조·억·%·반올림 오탐 감소               (추후)
5단계 자리표시자 구조   → 숫자는 코드가 채움, 환각 구조적 0       (추후)
```

- **구현 현황**: 1·2단계는 사업의 내용 답변과 상세 보고서(FR-016)에 적용했다(측정은 6절). 채팅의 재무 표와 요약 문장은 코드가 만들기 때문에 환각이 구조적으로 없다. 3단계(항목·값 쌍 대조)의 대상은 LLM이 재무 숫자를 쓰는 상세 보고서이고, 평가 세트와 함께 따로 한다.
- **2단계의 한계**: 숫자 값이 근거에 있기만 하면 통과한다(다른 항목의 숫자여도). 단위·표기만 다른 같은 값(131조 ↔ 131,895,033백만원)과 LLM이 더한 합산 값은 걸린다. 날짜(`2026.06.30`·`'26.1.1`)는 년·월·일로 쪼개 대조한다.

### 가져오지 않은 것

| 항목 | 이유 |
|---|---|
| LLM·Llama Guard로 안전 판정 | 판정을 LLM에게 맡기지 않는 원칙. Llama Guard는 t3.small에서 무거움 |
| LangGraph interrupt(사람 승인) | AI 그래프 안에 실행 도구가 남음. SMART는 실행 권한 자체를 뺌 |
| Mem0 장기 기억 | 현재 대화 맥락만 유지 |
| Ragas·TruLens로 가드레일 측정 | 지표가 RAG 답변 품질용이고 LLM 채점이라 결과가 흔들림. 가드레일은 차단율·오탐률, 숫자 가드는 재무 테이블로 자동 채점 |

### 운영·관측

- **호출 횟수 제한**: Spring에서 사용자별 채팅 호출 제한. MVP는 메모리 카운터(사용자당 분당 10회), 서버를 늘리면 Redis로 옮긴다.
- **로그**: 판정 코드와 노드별 소요 시간을 자체 로그 테이블(`chat_log`: thread_id, guard, node_ms, created_at)에 기록한다. 메시지 본문은 남기지 않는다. 응답을 보낸 뒤 백그라운드로 쓰고, 쓰기에 실패해도 채팅은 무관하다. 노드 시간은 그래프 스트림 이벤트 사이 간격이다.
  - 실측(로컬, 실제 OpenAI): 의도 추출 2.3~2.5초, 사업의 내용 답변 6.9초, 일반 답변 1.6초, 재무 조회 29ms, 가드 노드 1~2ms

### 테스트 구성

**API 단위**(개선 이야기를 수치로)와 **전체 시나리오**(서비스 목표 확인)를 둘 다 한다.
LLM은 "우리 서버의 한계를 재는가, 실제 사용자 경험을 확인하는가"로 나눈다.

| 테스트 | 대상 | LLM | 판정 |
|---|---|---|---|
| 지연 실측 | OpenAI 호출 | 실제 | p50·p95·분포 기록 → 가짜 LLM 입력값 |
| 성능 | 송금 내역 목록(전체 → 오프셋 → 커서) | — | p95 < 500ms |
| 부하 | 전체 시나리오, 목표 93 TPS 유지 | 가짜 | 일반 API p95 < 500ms, 채팅 p95 < 가짜 지연 p95 + 1초, 에러율 < 1% |
| 스트레스 | 약 4,960 VU부터 무너질 때까지 늘림(최소 34,608명까지 확인) | 가짜 | 한계 TPS 기록 → 최대 피크 집중도 역산 |
| 로드맵 비교 | 채팅 메시지: REST(RestClient) → 비동기(WebClient) | 가짜 | 단계별 처리량·스레드 비교 |
| 캐시 비교 | 채팅 메시지: 캐시 없음 → 프로세스 캐시(→ Redis) | 가짜 | 히트율별 p95·LLM 호출 수 비교 |
| 정합성 | 송금 확정 동시 요청(같은 요청ID 연타, 같은 계좌 동시 출금) | — | SQL 3개: 전체 잔액 합계 불변 / 중복 확정 0 / 음수 잔액 0. 락 없는 버전(기준선)·`FOR UPDATE`·`@Version`과 위반 건수·TPS 비교(측정 브랜치에서만) |
| 실제 검증 | 전체 시나리오, 목표 TPS의 10%로 5분 | 실제 | 판정 없이 기록(체감 시간, OpenAI 에러) |
| 품질 평가 | 아래 평가 세트 | 실제 | 첫 버전이 기준선, 단계마다 같은 세트로 전후 비교 |

품질 평가 세트(단계는 하나씩 추가하며 측정):

| 대상 | 지표 | 단계 |
|---|---|---|
| 숫자 환각 (NFR-016) | 환각률 | 5절 숫자 가드 1~3단계 |
| 송금 발화 (NFR-014) | 금액·수취인 일치율, 되묻기 재현율, 틀린 확인 카드 수(목표 0) | LLM 추출만 → 스키마 검증 → 원문 대조 |
| 인젝션 (NFR-012) | 차단율(공격 세트), 오탐률(정상 세트) | 규칙만 → (추후) Prompt Guard |
| 질문 인식 (NFR-044) | 의도 분류 정확도, 기업명 인식률(구어 표현 포함) | 정식 기업명 일치 → (문제가 확인되면) 별칭 사전 → 오타 허용 |
| 본문 검색 (NFR-039) | Recall@5, MRR | 벡터만 → (문제가 확인되면) BM25(RRF) → 재순위 |

- **기업명 인식 기준선**(`ai/evals/company_names.py`, 20개 발화 × 3회, gpt-5-nano·추론 강도 low, 2026-10-15): 재무 의도 100%(20/20), 기업명 인식(정식 이름 일치) 평균 52%(범위 9~12/20). 실패는 줄임말·구어 표기(삼전·하닉·현대차·네이버·한전 등)와 DART 법인명 차이(`한국전력`→`한국전력공사`)다. 정식명 변환·별칭 사전은 같은 세트·같은 방식으로 전후를 잰다.
- **숫자 환각 기준선**(`ai/evals/business_numbers.py`, 질문 20개 × 3회, gpt-5-nano·추론 강도 low, 로컬 실데이터 30곳, 2026-10-16): 숫자가 든 답변 평균 18.3/20 중 **근거에 없는 숫자가 든 답변 평균 1.7/20(8%, 범위 1~2)**. 가드 없이 나갔을 때의 1단계 기준선이다. 정답이 공시 본문 안에 있어 자동 채점된다.
  - 걸린 숫자: 삼성바이오로직스 수주 규모 1,471.5(3회 중 3회), 케이티 5006(1회), 기아 보고 기간을 `26.01.01` 꼴로 바꿔 쓴 날짜 2건(각 1회). 앞선 실행에서는 한화에어로스페이스 수주잔고 두 값을 더한 70,030,362와 크래프톤 지역별 매출 합산도 걸렸다.
  - 삼성바이오로직스는 정답인 수주총액 표(수주총액 21,689·수주잔고 9,923 백만달러)가 상위 5개에 들지 못해서 모델이 없는 숫자를 만든 경우다. 질문을 '수주총액과 수주잔고'로 바꾸면 그 표가 1위로 잡힌다. 검색 개선은 NFR-039에서 같은 세트로 전후를 잰다.
  - 2단계 가드는 걸린 답변을 고정 문장 + 출처로 바꾼다. 나가는 답변의 근거 없는 숫자는 0이 되고, 대신 표기·합산처럼 맞는 값도 막힌다(오탐 성격). 이것이 4단계 표기 정규화와 계산 코드의 근거다.
- **본문 의도 기준선**(13개 발화 × 3회, gpt-5-nano·추론 강도 low, 2026-10-16): 사업의 내용 21/24(88%), 재무·내역·송금·일반 15/15. 실패는 '투자 계획'(3회 중 2회)·'시장점유율'(3회 중 1회)이 재무로 간 경우다. 같은 프롬프트로 기업명 인식 세트를 다시 돌려 재무 의도 100%(20/20), 기업명 인식 평균 57%(범위 11~12/20)로 기준선과 차이가 없음을 확인했다.

- **LLM 지연 실측**(NFR-029, `ai/evals/llm_latency.py`, 호출 종류마다 30회·동시 4개, gpt-5-nano·추론 강도 low, 로컬 실데이터, 2026-10-16): 앱이 쓰는 함수와 프롬프트를 그대로 불러 OpenAI 호출 시간만 쟀다. 분포는 `ai/loadtest/latency.json`에 남는다(p95는 30개 중 29번째).

  | 호출 | 쓰이는 곳 | p50 | p95 | 최대 |
  |---|---|---|---|---|
  | 의도 추출(구조화 출력) | 모든 채팅 턴 | 2,953ms | 4,196ms | 4,426ms |
  | 일반 답변 | 일반 질문 | 2,834ms | 5,023ms | 5,408ms |
  | 사업의 내용 답변 | 사업의 내용 질문(일반 질문 꼴) | 5,000ms | 7,817ms | 8,800ms |
  | 상세 보고서 | 상세 보기 | 12,853ms | 22,790ms | 23,338ms |
  | 임베딩 | 사업의 내용 검색 | 175ms | 691ms | 838ms |

  - **지연은 시간에 따라 흔들린다.** 같은 날 같은 입력으로 상세 보고서를 다섯 번 재니 p50이 9.6초 → 12.2 → 10.7 → 13.6 → 12.9초였다. 그래서 분포는 측정 시점의 스냅샷이고, 부하 테스트 결과는 어느 분포 아래에서 잰 값인지 함께 적는다. 상세 보고서 p95가 22.8초까지 올라 상세 보기의 읽기 제한(30초)에 가깝다.
  - **질문 꼴이 지연을 바꾼다.** 처음에는 사업의 내용 질문을 숫자 질문(평가 세트)으로 쟀고 p50이 2.6초였다. 부하 시나리오와 같은 일반 질문("사업 내용 알려줘")으로 바꾸니 5.0초였다. 같은 시간에 상세 보고서가 9.6 → 12.9초로 34% 오른 것보다 크게 올랐으니 질문 꼴의 영향이 있다고 본다.
- **가짜 LLM**(`ai/loadtest/fake_llm.py`): OpenAI 호환 서버다. 앱 코드는 그대로 두고 환경변수만 바꾼다 — 가짜는 `uvicorn loadtest.fake_llm:app --port 9000`(`ai/`에서), FastAPI는 `OPENAI_BASE_URL=http://<가짜>:9000/v1`·`OPENAI_API_KEY=아무 값`.
  - `/v1/chat/completions`(일반 답변·구조화 출력)와 `/v1/embeddings`만 흉내 낸다. 요청 모양(구조화 출력 여부, 프롬프트의 `<공시>`·`<표>`)으로 호출 종류를 가려 위 분포에서 지연을 뽑는다.
  - 종류마다 시드 고정 난수열을 따로 쓴다(`FAKE_LLM_SEED`, 기본 1). 호출이 섞여도 종류별 순서는 같다. 지연은 `asyncio.sleep`이라 동시 호출이 많아도 OpenAI처럼 스레드를 잡지 않는다.
  - 의도 추출은 시나리오 문장 꼴(송금·내역·재무·사업)을 알아듣는 규칙 기반이고, 답변은 정해진 글이다(숫자가 없어 숫자 가드를 건드리지 않는다). 의도 인식 품질은 실제 LLM으로 `evals/`가 잰다. 앱 이미지에는 넣지 않는다.
- **가짜 vs 실제**(`ai/evals/fake_llm_check.py`, 턴마다 20회·동시 4개, 지연 실측 직후 두 번): 같은 채팅 턴을 실제 OpenAI와 가짜로 돌려 p50을 비교했다.

  | 턴 | 실제 p50 | 가짜 p50 | 차이(1회차 · 2회차) |
  |---|---|---|---|
  | 재무 비교 | 2,686 · 3,057ms | 2,917 · 2,936ms | +9% · −4% |
  | 사업의 내용 | 6,951 · 6,655ms | 7,329 · 7,326ms | +5% · +10% |
  | 상세 보고서 | 11,662 · 11,251ms | 12,701 · 12,698ms | +9% · +13% |
  | 일반 답변 | 3,673 · 4,309ms | 5,798 · 5,796ms | +58% · +35% |

  - 부하 시나리오에 나오는 턴은 가짜가 실제와 −4%~+13% 안이다. p95는 사업의 내용·상세 보고서가 ±10% 안이고, 재무 비교는 가짜가 낮았다(4.2초 vs 5.3~7.0초 — 20회라 p95는 꼬리 한두 개에 좌우된다).
  - 일반 답변 턴은 가짜가 35~58% 느리다. 분포에는 답이 긴 질문("예금과 적금의 차이가 뭐야?" 3.7초)이 섞여 있어, "안녕"(1.6초)처럼 짧은 질문이 많은 묶음보다 느리게 나온다. 일반 질문은 부하 시나리오에 없다.
  - 처음 분포(사업의 내용을 숫자 질문으로 쟀을 때)로 비교하면 사업의 내용 턴이 −29%·−34%, 상세 보고서가 −14%·−26%로 가짜가 빨랐다. 질문 꼴을 맞춰 다시 재고 실측 직후에 비교한 것이 위 표다.
- **OpenAI 429**(실제 구간): 우리 에러와 분리 집계, 재시도 없음. 실행 전 예상 비용(호출 수 × 토큰 단가)을 기록한다.
- **추론 강도**(`OPENAI_REASONING_EFFORT`): gpt-5-nano로 호출당 지연을 실제로 쟀다 — 기본(medium) 4~11초, low 약 2.7초, minimal 약 1.2초. minimal은 의도 추출을 자주 놓쳐(13건 중 3건) low를 기본으로 쓴다. 송금 발화 평가 세트는 이후에 같은 방식으로 잰다.
- **측정 환경**: 앱(Spring·FastAPI·PostgreSQL)만 t3.small 사양으로 제한하고, k6·Prometheus·Grafana는 제한 밖에 둔다.
- **LLM이 들어간 측정**: 같은 세트를 3번 돌려 평균·범위를 적는다. "0건"은 "100건 중 0건"처럼 분모와 함께 쓴다.

### 지표 수집

```text
k6 ──remote write──────────────────────────┐
Spring Actuator (HTTP 지연·Tomcat 스레드·DB 커넥션 풀) ─┤
FastAPI (LLM 호출 시간·OpenAI 에러 수·가드 판정 횟수) ──┼──▶ Prometheus ──▶ Grafana (한 화면, 같은 시간축)
postgres_exporter (커넥션·락 대기) ─────────────────────┤
cAdvisor (컨테이너 CPU·메모리) ───────────────────────┘
```

### E2E 테스트(JSP 화면)

- **도구**: Playwright for Java. 서버(Java/Gradle)·AI(Python) 둘뿐인 프로젝트에
  세 번째 언어 툴체인(Cypress 등)을 또 들이지 않는다 — 기존 JUnit 5 테스트와
  같은 언어·같은 명령(`./gradlew test`)으로 돈다. 브라우저 바이너리를 자동
  설치해서 별도 드라이버 관리가 거의 없다(Selenium 대비 장점).
- **실행 방식**: `@SpringBootTest(webEnvironment = RANDOM_PORT)`로 실제
  서버를 띄우고, 기존 `TestcontainersConfiguration`(PostgreSQL)을 그대로
  재사용해 Playwright가 그 포트에 브라우저로 접속한다. 새 인프라를 안 만들고
  이미 있는 테스트 기반 위에 얹는다.
- **범위**: 화면(JSP)이 있는 기능마다 만든다. 지금은 회원가입 → 로그인,
  계좌 개설·충전·대표 변경, 송금 내역(무한 스크롤), 별칭 등록·목록, 채팅 송금
  (메시지 → 확인 카드 → 비밀번호 → [보내기]), 채팅 대화 유지(메뉴를 다녀와도·
  [새 대화]), 로그아웃이다. 채팅의 AI 자리는 가짜
  FastAPI로 대체하고, 확인 카드의 요청ID와 송금·잔액은 실제 Spring·PostgreSQL로
  확인한다. 화면이 없는 기능은 API 통합 테스트로 충분하고, 화면이 생기는
  시점에 그 이슈에서 E2E도 같이 추가한다(AGENTS.md 참고).

## 8. 기술 스택

| 구분 | 기술 |
|---|---|
| 화면 | JSP (로그인·회원가입, 채팅, 계좌·충전, 송금 내역, 별칭) + 공통 CSS(현대닷컴 톤) |
| 백엔드 | Spring Boot 4.1.1, Java 17, JPA, JWT. FastAPI 호출: RestClient(1단계) → WebClient(2단계) |
| AI | FastAPI, LangGraph, OpenAI(LLM·임베딩) |
| DB | PostgreSQL 하나 (회원·계좌·송금 + 재무 테이블 + pgvector) |
| 배포 | Docker Compose로 로컬 실행(Spring Boot·FastAPI 모두). 홈서버: `main` 머지 시 GitHub Actions가 이미지를 빌드해 Docker Hub에 올리고 SSH로 pull·재실행 → 추후 AWS EC2 |
| 테스트·모니터링 | k6(Prometheus remote write), Prometheus(Spring Actuator·FastAPI·postgres_exporter·cAdvisor), Grafana |

### 쓰지 않는 기술과 도입 조건

기술은 필요할 때 도입하고 근거를 남긴다(1절). 지금 쓰지 않는 이유와 도입 트리거를 적어 둔다.

| 기술 | 지금 쓰지 않는 이유 | 도입 조건 | 도입하면 잴 것 |
|---|---|---|---|
| **nginx** (리버스 프록시) | Spring이 JSP와 API를 직접 서빙하고(8080) FastAPI는 내부 전용이라 앞단이 맡을 일이 없다. 인스턴스가 1대라 분산할 곳도 없다. 앞단을 넣으면 모든 측정에 변수가 하나 늘어 "한 번에 하나만 바꿔 효과를 수치로"(2절) 원칙에도 어긋난다 | AWS EC2 이전과 함께 HTTPS 종단이 필요할 때, 인스턴스 2대 이상으로 부하를 나눌 때, 정적 파일 분리·압축이 측정으로 필요하다고 드러날 때 | 정적 응답 p95, TLS 포함 지연, 업스트림 연결 재사용 효과 |
| **Redis** | 캐시할 만한 곳은 LLM 호출이 지연의 대부분(2~7초)이라 저장소가 ms 단위인지는 문제가 아니다. 지금은 인스턴스 1대·FastAPI 워커 1개라 프로세스 내 캐시와 메모리 카운터로 충분하다. 컨테이너가 하나 늘면 t3.small(2GiB) 한도 안에서 JVM·PostgreSQL·FastAPI와 메모리를 나눠 쓰고, 운영 대상(장애·보안)도 늘어난다 | 2절 4단계의 (a)~(c): 인스턴스 2대 이상, 재시작 때 캐시 손실, 프로세스 메모리 초과 | 히트율, p50·p95, LLM 호출 수, 1천 채팅당 비용 |

## 9. 아키텍처 / 흐름

### 전체 구성

```text
[JSP] ◀──▶ [Spring Boot] ◀──내부 REST──▶ [FastAPI + LangGraph]     [FastAPI 스케줄러]
                 │                               │                        │
                 ▼                               ▼                        ▼
      [PostgreSQL: 회원·계좌·송금 | 재무 테이블 | pgvector(사업의 내용)] ◀──┘
```

### LangGraph 워크플로우 (큰 흐름)

```text
사용자 메시지
   ▼
[의도 분류]
   ├─ 송금   ──▶ Spring 송금 요청 생성 ──▶ 확인 카드 반환
   ├─ 내역   ──▶ Spring 내역 조회 ──▶ 설명
   └─ DART   ──┬─ 재무 테이블 ──▶ 계산 코드(수치·경쟁사 비교) ──▶ 요약 + 표
               └─ pgvector 검색(사업의 내용) ──▶ 요약
```

### 채팅 송금

```text
JSP ─"엄마한테 1만원"─▶ Spring ─▶ FastAPI(LangGraph) ─송금 요청 생성─▶ Spring
                                                      (요청ID 발급, 금액·수취인 고정 저장)
JSP ◀──────────────── 확인 카드(요청ID) ────────────────────────────────┘
JSP [보내기] ─요청ID + 계좌 비밀번호─▶ Spring: 본인 확인 → 비밀번호 확인 → 트랜잭션(잔액 차감·입금·내역 기록)
```

### DART 수집

```text
[매일] FastAPI 스케줄러 전용 컨테이너(collector)
       다중회사 주요계정 API(최근 2년 8개 기간) ─▶ 재무 테이블
       공시서류원본파일 API ─▶ "사업의 내용" 추출 ─▶ 청킹 ─▶ OpenAI 임베딩 ─▶ pgvector
       (정정본은 덮어쓰기, 사업의 내용은 회사별 최신 보고서만)
```
